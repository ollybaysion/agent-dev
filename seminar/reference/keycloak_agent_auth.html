Keycloak 기반 AI 에이전트 권한 구조

Role이 어디에 정의되고, 어떻게 토큰에 담겨, 어떤 경로로 API까지 전달되는지 다섯 장의 그림으로 설명합니다.

Keycloak (인증·인가 서버) 토큰(JWT)과 그 내용 애플리케이션·서비스

그림 1전체 구성: 누가 어디에 있는가

그림 2가장 단순한 흐름: 에이전트가 서비스 계정으로 동작 (모델 A)

그림 3사용자를 대신하는 흐름: 토큰 교환 (모델 C, RFC 8693)

그림 4멀티 에이전트로 확장: 권한을 좁혀서 내려보내기

그림 5Role이 토큰에 들어가는 경로 (Keycloak 내부)

정리표: Role은 어디에 있나

구분위치
Role 정의와 매핑Keycloak DB (관리 콘솔, realm export JSON, Admin REST API로 관리)
Role이 토큰에 들어가는 규칙Keycloak의 Client Scope → Protocol Mapper 설정
실제 전달액세스 토큰(JWT) payload의 realm_access / resource_access 클레임
요청 시 위치HTTP Authorization: Bearer <JWT> 헤더 (본문 아님)
검증 주체토큰을 받는 API 서버가 서명 검증 후 클레임을 읽음

한 줄 요약: Role은 Keycloak 설정(DB)에 살고, 토큰 발급 순간 JWT 안에 복사되어, HTTP 헤더에 실려 API까지 가며, API는 서명만 검증하고 그 값을 믿습니다.
