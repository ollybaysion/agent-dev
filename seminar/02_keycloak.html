Keycloak — IdP를 직접 운영하기

Realm · Client · Role이 토큰의 어떤 값이 되는가

대상: Java/Spring 경험이 있는 에이전트 개발자 · 사전 지식: 1회차(SSO · OIDC · JWT) · 50분

지난 회차 복습 — 세 가지만 기억하면 된다

IdP (Identity Provider)

로그인을 맡는 한 곳. 앱은 로그인 화면을 만들지 않고 IdP가 발급한 토큰만 믿는다.

오늘의 IdP = Keycloak

Authorization Code 흐름

브라우저는 code만 받고, 앱 서버가 code + secret으로 토큰을 받는다 (백 채널).

토큰이 URL에 남지 않는다

JWT 서명 검증

토큰은 IdP의 개인키로 서명된다. API는 공개키로 검증하므로 요청마다 IdP에 물어볼 필요가 없다.

header . payload . signature

오늘은 이 IdP를 직접 설치·설정하고, 설정한 값이 토큰 안의 어떤 필드가 되는지, Spring이 그것을 어떻게 검증하는지 본다.

오늘의 목표

  1. Keycloak의 핵심 객체(Realm, Client, User, Role, Scope, Mapper)가 무엇이고 서로 어떻게 연결되는지 그림으로 설명할 수 있다.
  2. 관리 콘솔에서 설정한 Role이 JWT의 어느 클레임에 어떤 모양으로 들어가는지 안다.
  3. Spring Boot API를 Resource Server로 만들어 토큰 서명 · aud · Role을 검증하고, 에이전트용 Service Account로 토큰을 받아 호출할 수 있다.

오늘 다루지 않는 것

  • 브라우저(FE)에 토큰을 두는 문제 → 3회차 BFF
  • 에이전트가 사용자를 대신하는 문제 → 4회차 A2A
  • 운영 배포(HA, DB, TLS) → 참고 자료

Keycloak이란 — 오픈소스 IdP

  • 2014년 Red Hat(JBoss)에서 시작, 2023년 CNCF(클라우드 네이티브 컴퓨팅 재단) 프로젝트로 이관. Apache 2.0 라이선스

  • 사내 서버·컨테이너에 직접 설치(온프레미스) 가능 → 인증 데이터를 밖으로 내보내기 어려운 기업 환경에서 선택

전체 구조 — Keycloak은 토큰을 발급하고, 검증용 공개키를 제공한다

02

핵심 개념

Realm → Client → User · Role → Scope · Mapper → 토큰. 설정 화면의 메뉴 순서와 같다.

핵심 객체 지도 — 모든 것은 Realm 안에 있다

Realm (렐름)

  • 사용자·클라이언트·역할의 격리 단위. realm이 다르면 서로 보이지 않는다
  • company-dev, company-prod처럼 환경별로 분리
  • master realm은 관리 전용 — 여기에 앱을 등록하지 않는다
  • URL에 그대로 드러난다: /realms/company/…

관리 콘솔: 왼쪽 위 realm 선택 → 왼쪽 메뉴가 오른쪽 그림의 상자들이다.

Client — Keycloak에 등록된 앱·에이전트·API

설정 (관리 콘솔)의미켜는 경우

오늘 만들 client 세 개

web-app (Standard flow) · report-agent (Service accounts) · report-api (토큰 검증만 — 플로우 전부 OFF, aud 이름과 client role 보관용)

User vs Service Account — 사람과 프로그램은 토큰을 다르게 받는다

Role — 정의한 역할은 토큰의 두 자리에 들어간다

"Role이 어디서 오느냐"에 대한 답. 관리자가 Keycloak에 저장 → 발급 시 JWT에 복사 → Bearer 헤더로 API에 도착. 코드나 config에는 없다. composite는 펼쳐져서 들어간다는 점, client role은 resource_access 아래 client 이름으로 묶인다는 점을 짚는다.

Group과 Composite — 권한은 기능 단위로, 묶음은 설정으로

  • Group: 조직 단위. 그룹에 역할을 매핑하면 소속 사용자가 모두 상속
  • Composite role: 역할을 묶은 역할. admin = agent:report + agent:audit + …
  • 토큰에는 둘 다 펼쳐진 최종 역할만 들어간다

권장 설계

코드는 hasRole('agent:audit')처럼 기능 단위 역할만 본다. "admin도 쓰게 해 달라", "user도 audit 에이전트 허용"은 Keycloak 설정 변경으로 끝난다 — 배포 없음.

if (roles.contains("admin"))처럼 사람 등급을 코드에 박으면 정책이 바뀔 때마다 배포해야 한다.

Client Scope와 Protocol Mapper — "토큰에 무엇을 넣을지"

Audience 매퍼는 직접 추가해야 한다

Keycloak 기본 access token의 aud에는 호출 대상 API가 없다(보통 account만). report-api를 넣으려면 client의 dedicated scope에 Audience 매퍼를 추가한다. 이게 없으면 20장의 aud 검증이 항상 실패한다.

커스텀 클레임

부서, 사번 같은 값은 User Attribute 매퍼로 넣는다. 단, 토큰은 누구나 디코딩할 수 있으니 민감 정보는 넣지 않는다.

실습에서 가장 많이 막히는 지점이 aud다. Spring에서 audience 검증을 켰는데 403/401이 나면 십중팔구 Audience 매퍼 누락. 토큰을 디코딩해서 aud 배열을 보여 주며 설명.

토큰 발급 두 경로 — 사람은 code로, 에이전트는 자격으로

API 쪽 = Resource Server (토큰 검증) · 에이전트 쪽 = OAuth2 Client (토큰 획득)

spring:

    oauth2:

issuer-uri 하나로 자동

  • discovery 문서 → jwks_uri → 공개키 캐시
  • 요청마다 서명 · exp · iss 검증
  • 실패하면 Controller 전에 401

자동으로 안 되는 것

  • aud 검증 (기본 OFF) → 20장
  • Keycloak roles → Spring 권한 변환 → 19장

SecurityConfig — Controller 앞, 필터 체인에서 끝낸다

SecurityConfig.java

@Configuration
@EnableMethodSecurity            // @PreAuthorize 활성화 (없으면 조용히 무시)
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())         // 순수 Bearer API 일 때만
            .sessionManagement(s -> s.sessionCreationPolicy(
                SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health").permitAll()
                .requestMatchers(HttpMethod.POST, "/reports/**")
                    .hasRole("report-writer")
                .anyRequest().authenticated())
            .oauth2ResourceServer(rs -> rs.jwt(jwt ->
              jwt.jwtAuthenticationConverter(keycloakConverter())));
        return http.build();
    }
}

요청이 지나가는 순서

BearerTokenAuthenticationFilter(토큰 추출·검증) → Converter(roles 변환) → AuthorizationFilter(URL 규칙) → Controller → @PreAuthorize

401 vs 403

401 토큰 없음·서명/만료 실패 · 403 토큰은 맞지만 역할 부족

hasRole("x")는 권한 ROLE_x를 찾는다 → 변환기가 접두어를 붙여야 한다.

"Controller 앞인가?"라는 질문의 답: Servlet Filter 단계. Controller 코드에서 Authorization 헤더를 직접 파싱하지 않는다. csrf.disable()은 쿠키 세션이 없을 때만 허용되며, 3회차 BFF에서는 다시 켠다.

roles 변환기 — Keycloak 클레임을 Spring 권한으로

SecurityConfig.java (계속)

private JwtAuthenticationConverter keycloakConverter() {
    var scopes = new JwtGrantedAuthoritiesConverter();  // scope → SCOPE_x
    var converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(jwt -> {
        List<GrantedAuthority> out = new ArrayList<>(scopes.convert(jwt));
        roles(jwt.getClaimAsMap("realm_access"))      // realm role
            .forEach(r -> out.add(role(r)));
        Map<String, Object> res = jwt.getClaimAsMap("resource_access");
        if (res != null) res.values().forEach(v ->   // client role
            roles((Map<String, Object>) v).forEach(r -> out.add(role(r))));
        return out;
    });
    return converter;
}

private static GrantedAuthority role(String r) {
    return new SimpleGrantedAuthority("ROLE_" + r);
}

@SuppressWarnings("unchecked")
private static List<String> roles(Map<String, Object> access) {
    if (access == null) return List.of();
    return (List<String>) access.getOrDefault("roles", List.of());
}

왜 필요한가

Spring 기본 변환기는 scope 클레임만 읽는다. Keycloak의 역할은 realm_access.roles에 있으므로 직접 꺼내 ROLE_를 붙인다.

결과 권한 예

ROLE_agent:report
ROLE_report-writer
SCOPE_report:write

공통 라이브러리(starter)로 만들어 두면 팀마다 복붙하지 않는다.

aud 검증기 — 다른 서비스용 토큰을 거절한다

JwtConfig.java

@Bean
JwtDecoder jwtDecoder(OAuth2ResourceServerProperties props) {
    String issuer = props.getJwt().getIssuerUri();
    NimbusJwtDecoder decoder = JwtDecoders.fromIssuerLocation(issuer);
    var withIssuer = JwtValidators.createDefaultWithIssuer(issuer);
    var audience   = new AudienceValidator("report-api"); // + aud 검사
    decoder.setJwtValidator(
        new DelegatingOAuth2TokenValidator<>(withIssuer, audience));
    return decoder;
}

static class AudienceValidator implements OAuth2TokenValidator<Jwt> {
    private final String expected;
    AudienceValidator(String expected) { this.expected = expected; }

    @Override
    public OAuth2TokenValidatorResult validate(Jwt jwt) {
        if (jwt.getAudience().contains(expected))
            return OAuth2TokenValidatorResult.success();
        return OAuth2TokenValidatorResult.failure(new OAuth2Error(
            "invalid_token", "aud 불일치: " + expected, null)); // → 401
    }
}

없으면 생기는 일

같은 realm의 search-api용 토큰, 또는 다른 에이전트의 토큰이 그대로 통과한다. 서명도 iss도 모두 정상이기 때문이다.

짝: Audience 매퍼

Keycloak 쪽에서 report-api를 aud에 넣어 주어야(12장) 이 검증을 통과한다.

Boot 속성 jwt.audiences는 이 코드의 축약판이다.

4회차 "aud 불일치 → 거절" 그림의 구현이 바로 이 코드. 토큰이 "어느 API를 위해 발급되었는가"를 API 스스로 확인하는 것이며, 멀티 에이전트에서 토큰을 서로 돌려쓰는 것을 막는 장치다.

어노테이션이 못 하는 것

"이 보고서가 kim의 것인가"(데이터 소유) 는 서비스 코드에서 직접 검사한다. 역할만 보면 남의 ID를 넣어 조회하는 IDOR가 뚫린다.

에이전트용 Service Account 만들기 — 콘솔 6단계 + curl

  1. Clients → Create client · Client ID report-agent → Next
  2. Capability config: Client authentication ON, Service accounts roles ON, Standard flow OFF → Save
  3. Credentials 탭 → Client secret 복사 → 비밀 저장소(Vault, 환경 변수)에
  4. Service accounts roles 탭 → Assign role → agent:report, report-api / report-writer
  5. Client scopes 탭 → report-agent-dedicated → Add mapper → By configuration → Audience → Included Client Audience report-api, Add to access token ON
  6. curl로 토큰 요청 → payload의 aud, azp, realm_access.roles 확인

실습 (Keycloak :8180, API :8080)

TOKEN=$(curl -s -X POST \
  http://localhost:8180/realms/company/protocol/openid-connect/token \
  -d grant_type=client_credentials \
  -d client_id=report-agent \
  -d client_secret="$REPORT_AGENT_SECRET" | jq -r .access_token)

# payload 만 디코딩해서 확인
# (로컬 실습 토큰만! 운영 토큰을 외부 디코더 사이트에 붙여 넣지 말 것)
echo "$TOKEN" | cut -d. -f2 | tr '_-' '/+' \
  | base64 -d 2>/dev/null | jq

# API 호출 → 200. 역할을 빼고 다시 받으면 403, 토큰 없이면 401
curl -i http://localhost:8080/reports \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"title":"test"}'
라이브 데모 포인트: 5단계(Audience 매퍼)를 건너뛰고 토큰을 받아 aud가 ["account"]뿐인 것을 보여 준 뒤, 매퍼를 추가하고 다시 받아 report-api가 생기는 것을 비교. 토큰 수명이 5분이라 데모 중 만료될 수 있으니 미리 말해 둔다.

AgentHttpConfig.java

@Bean   // Boot 가 자동 구성해 주는 버전이면 생략 가능
OAuth2AuthorizedClientManager clientManager(
        ClientRegistrationRepository regs,
        OAuth2AuthorizedClientService clients) {
    var manager = new AuthorizedClientServiceOAuth2AuthorizedClientManager(
        regs, clients);
    var provider = OAuth2AuthorizedClientProviderBuilder.builder()
        .clientCredentials().build();
    manager.setAuthorizedClientProvider(provider);
    return manager;              // 만료되면 알아서 새 토큰을 받는다
}

    oauth2.setClientRegistrationIdResolver(request -> "report-agent");
    return RestClient.builder()
        .baseUrl("https://report-api.company.com")
        .requestInterceptor(oauth2)  // Authorization: Bearer 자동 첨부
        .build();
}
// 6.4 미만: WebClient +
//   ServletOAuth2AuthorizedClientExchangeFilterFunction
에이전트 코드에는 토큰 문자열이 등장하지 않는다. 인터셉터가 요청마다 유효한 토큰을 붙이고, 만료 전에 다시 받는다. secret은 환경 변수나 Vault에서만 온다.

권한 모델 정리 — 언제 무엇을 쓰나

모델답하는 질문Keycloak 설정Spring에서쓰는 때
Role (RBAC)이 주체가 무슨 역할인가Realm/Client role, composite, 그룹 매핑hasRole, @PreAuthorize대부분. 기능 단위 role로
Scope이 토큰으로 무엇까지 허용했나Client scope(report:write), 요청 scopehasAuthority('SCOPE_…')에이전트별 권한 축소 → 4회차
Authorization Services이 리소스에 이 조건으로 되나Resource · Scope · Policy · Permission (UMA 2.0)Policy Enforcer 또는 직접 질의시간·속성·소유 조건이 많을 때만. 복잡도 큼
데이터 소유 검사이 보고서가 kim의 것인가(Keycloak 밖)서비스 코드에서 직접항상. 역할만으론 못 막는다

이 시리즈의 선택

Role로 "누가 어떤 에이전트를 쓸 수 있나", Scope + aud로 "에이전트가 어떤 API를 어디까지", 코드로 "이 데이터가 그 사람 것인가".

Authorization Services는 보류

강력하지만 Keycloak에 정책이 쌓이면 디버깅이 어렵다. 역할·scope로 안 풀리는 요구가 실제로 나올 때 도입한다.

자주 하는 실수

❌ master realm에 앱 등록

master는 Keycloak 자체 관리용. 사고 나면 전체가 뚫린다. 업무 realm을 따로 만든다.

❌ 운영에서 start-dev

HTTP 허용, 내장 DB, 캐시 비활성. 운영은 start + PostgreSQL + TLS + --hostname.

❌ client secret을 git에

yml에 직접 쓰지 않는다. 환경 변수나 Vault. 유출 시 Credentials 탭에서 Regenerate.

❌ aud 미검증

같은 realm의 모든 토큰이 통과한다. 검증기(20장) + Audience 매퍼(12장)는 한 쌍.

❌ access token 수명을 길게

"자꾸 만료돼요"에 1시간으로 늘리지 말 것. 기본 5~15분 유지, 갱신은 refresh/client 라이브러리에.

❌ "admin" 문자열 하드코딩

사람 등급이 아니라 agent:audit 같은 기능 단위 역할을 검사한다. 정책 변경 = 설정 변경.

코드 쪽 함정(같은 클래스 내부 호출, @EnableMethodSecurity 누락)은 21장 참조.

요약 · 실습 과제 · 다음 회차

체크리스트

  • Realm은 격리 단위, master는 관리 전용
  • Client = 등록된 앱·에이전트·API. 에이전트는 Service account
  • Role은 Keycloak DB → 발급 시 JWT realm_access / resource_access
  • Scope·Mapper가 "토큰에 무엇을 넣을지" 결정. aud는 Audience 매퍼
  • API는 공개키로 로컬 검증. Keycloak에 요청당 호출 없음
  • Spring: issuer-uri + roles 변환기 + aud 검증기 + @PreAuthorize

실습 과제

  2. client report-api(검증용), report-agent(Service account) 생성, 역할·Audience 매퍼 설정
  3. curl로 토큰 받아 realm_access.roles, aud 확인
  4. Spring Resource Server에 붙여 200 / 403 / 401 재현
