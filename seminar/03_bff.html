에이전트 개발자를 위한 인증·인가 세미나 · 3회차

BFF — 토큰을 브라우저에 두지 않기

FE/BE 분리 구조에서 로그인과 토큰을 누가 맡는가

대상: Java/Spring 경험이 있는 에이전트 개발자 · 전제: 1·2회차(OIDC, Keycloak 토큰 발급·검증) · 50분

지난 시간 복습 — Keycloak이 발급하고, API가 검증한다

  • Keycloak이 로그인을 맡고 서명된 JWT를 발급한다
  • 호출자는 Authorization: Bearer <JWT> 헤더를 붙인다
  • API(Resource Server)는 Keycloak 공개키로 서명을 검증하고, 토큰 안의 역할로 허용 여부를 정한다
  • 역할 검사는 @PreAuthorize("hasRole('…')") 한 줄, aud 검증은 직접 추가
  • 요청마다 Keycloak에 물어보지 않는다 — 토큰이 스스로 증명한다

오늘의 목표

  1. 302와 401을 구분해서 응답할 수 있다 — 페이지 요청과 API 요청은 로그인 유도 방식이 다르다
  2. BFF(Backend For Frontend)를 Spring으로 만들 수 있다 — 로그인 대행, 토큰 보관·중계·갱신, 세션, CSRF, 로그아웃
  3. FE 담당자에게 넘길 최소 작업을 말할 수 있다 — 인터셉터 하나와 링크 두 개

이 회차가 끝나면

"토큰을 브라우저에 둘까, 서버에 둘까"라는 질문에 근거를 갖고 답할 수 있고, 그 답을 Spring 설정 20줄로 옮길 수 있다.

01

왜 필요한가

FE/BE가 나뉘면 토큰은 누가 들고 있나

문제 — 토큰은 누가 들고 있나?

  • FE(SPA)와 BE(API)가 분리된 구조
  • 로그인 화면은 Keycloak이 준다 (1·2회차)
  • 남은 질문: 토큰을 누가 받아서 보관하고, API 호출에 붙이나?
  • 권한 검사는 BE에만. FE의 버튼 숨김은 편의일 뿐 — 개발자 도구로 바꾸거나 curl로 우회된다

오늘의 질문

토큰을 브라우저에 둘 것인가, 서버에 둘 것인가.

FE에서 role을 보고 메뉴를 숨기는 것은 UX. 보안 경계는 항상 BE. 이 전제를 먼저 못 박아야 "FE에 뭘 구현해야 하나"라는 질문이 작아진다.

선택지 A — SPA가 토큰을 직접 보관한다

장점

  • 서버가 상태를 갖지 않는다 (stateless)
  • BE는 2회차의 Resource Server 그대로
  • 자료와 라이브러리가 많다

단점

  • 토큰을 JS가 읽는다 → XSS 한 줄이면 유출
  • secret 없는 public client
  • refresh token까지 브라우저에 → 피해 기간이 길다

PKCE(Proof Key for Code Exchange): secret이 없는 클라이언트가 code 가로채기를 막는 장치. 1회차 참고.

XSS가 "있으면 안 된다"는 건 맞지만, 서드파티 스크립트·마크다운 렌더링·에이전트가 생성한 HTML 등 SPA에서 XSS 가능성을 0으로 만들기는 어렵다. 그래서 토큰이 JS에 보이지 않는 구조가 필요하다.

선택지 B — BFF가 토큰을 대신 들고 있는다

BFF라는 말의 두 의미

원래: 웹·모바일 등 프런트엔드별 전용 백엔드(API 조합 계층). 보안 패턴: 토큰을 서버가 대신 보관하는 OAuth BFF — IETF "OAuth 2.0 for Browser-Based Applications"가 가장 안전한 방식으로 권장. 오늘은 후자.

핵심 한 줄

브라우저에는 쿠키만, 토큰은 서버에. FE는 토큰을 본 적이 없다.

BFF가 곧 업무 백엔드여도 된다(작은 시스템). API가 여러 개면 Gateway를 BFF로 둔다(슬라이드 18). 어느 쪽이든 "브라우저에 토큰이 없다"는 성질은 같다.

BFF가 하는 네 가지 일

XSS가 났을 때 — 무엇이 달라지나

구분SPA가 토큰 보관BFF
토큰 탈취가능 — JS가 읽는다불가 — HttpOnly 쿠키, JS가 못 읽는다
공격자가 쓰는 곳어디서든 (훔친 토큰을 다른 PC에서 재사용)피해자 브라우저 안에서만 (쿠키는 거기서만 자동 첨부)
피해 기간토큰 만료까지, refresh token까지 털리면 더 길게피해자가 그 페이지를 열어 둔 동안
서버에서 끊기어렵다 — 토큰은 자체 검증세션 삭제로 즉시
XSS 자체 방지안 됨안 됨 — 피해를 줄일 뿐

BFF는 XSS를 막지 않는다. 피해를 줄인다.

CSP, 출력 이스케이프, 에이전트가 생성한 HTML의 sanitize는 여전히 필요하다. BFF는 "뚫려도 토큰은 안 나간다"는 두 번째 방어선이다.

02

로그인 흐름

로그인 안 된 요청은 어떻게 Keycloak까지 갔다가 돌아오나

로그인 전체 흐름 — 401에서 200까지

③에서 FE가 직접 Keycloak 주소를 만들지 않는 점을 강조. FE는 BFF의 고정 경로(/oauth2/authorization/keycloak)만 안다. state·PKCE·redirect URI 조립은 전부 BFF. 1회차의 code flow가 그대로 들어 있다.

302와 401 — 페이지 요청과 API 요청은 다르게 응답한다

API 요청에 302를 주면?

fetch는 화면을 바꾸지 않고 백그라운드에서 302를 따라간다 → Keycloak 로그인 HTML을 JSON 대신 받아 파싱 오류, 또는 도메인이 달라 CORS 오류. 사용자 화면은 그대로다. 그래서 /api/**에는 401.

실무에서 가장 많이 겪는 증상: "로그인 세션이 끊기면 화면이 멈추고 콘솔에 Unexpected token '<' in JSON". 원인은 API 경로에 302가 나가는 것. Spring 기본값이 302라서 EntryPoint 분기(슬라이드 17)가 필요하다.

함정 — 403에 로그인 리다이렉트를 하면 무한 루프

규칙

  • 401 Unauthorized = 누구인지 모름 → 로그인으로
  • 403 Forbidden = 알지만 권한 없음 → 안내만, 이동 금지

BE도 구분해서 응답한다

세션·토큰 없음 → 401. @PreAuthorize 실패 → 403. Spring Security 기본 동작이므로 FE는 상태 코드만 믿으면 된다.

401과 403을 "둘 다 인증 에러"로 묶어 처리하는 FE 코드가 흔하다. 이름부터 다르다: Unauthorized는 사실상 Unauthenticated, Forbidden이 진짜 "권한 없음".

FE가 할 일 전부 — 인터셉터 하나, 링크 두 개

api.js — 전역 응답 인터셉터

axios.interceptors.response.use(
  res => res,
  err => {
    const status = err.response?.status;
    if (status === 401) {                       // 로그인 안 됨 → 로그인으로
      sessionStorage.setItem('returnTo', location.pathname);
      window.location.href = '/oauth2/authorization/keycloak';
    } else if (status === 403) {                // 권한 없음 → 안내만, 이동 금지
      toast('이 기능을 사용할 권한이 없습니다.');
    }
    return Promise.reject(err);
  }
);

// 로그인 후 첫 진입 시 (App.vue / index.js)
const back = sessionStorage.getItem('returnTo');
if (back) { sessionStorage.removeItem('returnTo'); router.replace(back); }

그 외

  • 로그인 링크: <a href="/oauth2/authorization/keycloak">
  • 로그아웃: POST /logout form (CSRF 토큰 포함, 슬라이드 21)
  • (선택) GET /api/me로 역할을 받아 메뉴 숨김 — 판단은 항상 BE

FE는 토큰을 본 적이 없다

Authorization 헤더를 붙이는 코드도, 갱신 코드도 없다. 쿠키는 브라우저가 자동으로 보낸다 (같은 출처면 withCredentials도 불필요).

03

Spring으로 BFF 만들기

로그인 대행 · 401 분기 · Gateway · 세션 · CSRF · 로그아웃 · 갱신 · 배치

의존성과 설정 — Keycloak 주소만 알려 주면 된다

의존성 (org.springframework.boot)

  • spring-boot-starter-web
  • spring-boot-starter-security
  • spring-boot-starter-oauth2-client ← BFF 핵심

Keycloak 쪽 설정

  • Client ID agent-portal, Client authentication ON (confidential)
  • Valid redirect URIs: https://app.company.com/login/oauth2/code/keycloak
  • Web origins는 비워 둔다 — 브라우저가 Keycloak을 fetch하지 않는다

application.yml

spring:
  security:
    oauth2:
      client:
        registration:
          keycloak:                      # ← 이 이름이 URL이 된다
            client-id: agent-portal
            client-secret: ${KEYCLOAK_CLIENT_SECRET}   # 환경변수. git 금지
            authorization-grant-type: authorization_code
            scope: openid, profile, email
        provider:
          keycloak:
            issuer-uri: https://keycloak.company.com/realms/company

registration 이름 keycloak → 로그인 시작 /oauth2/authorization/keycloak, 콜백 /login/oauth2/code/keycloak. issuer-uri 하나로 인증·토큰·JWKS 주소를 자동 조회한다.

SecurityConfig — 로그인은 자동, 401 분기만 직접

BffSecurityConfig.java

@Configuration
public class BffSecurityConfig {

    @Bean
    SecurityFilterChain bff(HttpSecurity http) throws Exception {
        var api = PathPatternRequestMatcher.withDefaults().matcher("/api/**");
        // Spring Security 6.5 미만: new AntPathRequestMatcher("/api/**")
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/index.html", "/assets/**").permitAll()
                .anyRequest().authenticated())
            .oauth2Login(Customizer.withDefaults())            // 슬라이드 11의 ④~⑧
            .exceptionHandling(ex -> ex
                .defaultAuthenticationEntryPointFor(            // /api/** 는 302 대신 401
                    new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED), api));
        return http.build();
    }
}

무엇이 자동인가

oauth2Login(): 302 조립(state, PKCE), 콜백 수신, code→토큰 교환, 세션 생성, 원래 페이지 복귀.

무엇을 직접 하나

EntryPoint 분기 한 줄. /api/**만 401, 나머지(페이지)는 기본값인 302.

CSRF는 끄지 않았다

기본값(켜짐) 유지. SPA용 설정은 슬라이드 20.

페이지 요청으로 로그인이 시작되면 Spring이 원래 URL을 세션에 저장해(RequestCache) 로그인 후 그리로 보낸다. API 401 → 인터셉터 경로로 시작되면 저장된 요청이 없어 "/"로 오므로 FE가 returnTo를 쓴다(슬라이드 14).

뒤에 API가 여러 개라면 — Spring Cloud Gateway를 BFF로

application.yml (Gateway)

spring:
  cloud:
    gateway:
      default-filters:
        - TokenRelay=     # 토큰 → Bearer
      routes:
        - id: report-api
          uri: http://report-api:8080
          predicates:
            - Path=/api/reports/**
        - id: agent-platform
          uri: http://agent-platform:8080
          predicates:
            - Path=/api/agents/**
# + 앞 슬라이드의 oauth2 client 설정 그대로
# 4.3+: spring.cloud.gateway.server.webflux.* 권장

의존성: spring-cloud-starter-gateway-server-webflux (4.3+) + spring-boot-starter-oauth2-client. WebFlux 기반 → SecurityWebFilterChain.

세션 — 토큰이 서버에 있으니 세션 저장소가 필요하다

application.yml

# 의존성: spring-session-data-redis
spring:
  data:
    redis:
      host: redis
  session:
    timeout: 8h          # idle 만료 (토큰과 별개)
server:
  servlet:
    session:
      cookie:
        name: SESSION
        http-only: true
        secure: true
        same-site: lax
  • Spring Session이 HttpSession을 Redis로 투명하게 교체 — 코드 변경 없음
  • 로컬 메모리 세션은 인스턴스 1대일 때만 동작

CSRF — 쿠키는 자동으로 붙으니 한 겹 더 필요하다

BffSecurityConfig.java (추가)

http
    .csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse()) // XSRF-TOKEN 쿠키
        .csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler()))   // 헤더 값 비교
    .addFilterAfter(new CsrfCookieFilter(), BasicAuthenticationFilter.class);

// 토큰을 한 번 읽어야 쿠키가 실제로 내려간다 (지연 로딩)
static class CsrfCookieFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        ((CsrfToken) req.getAttribute(CsrfToken.class.getName())).getToken();
        chain.doFilter(req, res);
    }
}

왜 필요한가

쿠키는 다른 사이트가 보낸 요청에도 자동 첨부된다 → 공격 사이트가 사용자 브라우저로 POST /api/transfer를 보낼 수 있다.

  1. XSRF-TOKEN 쿠키 발급 (HttpOnly 아님)
  2. axios가 X-XSRF-TOKEN 헤더로 복사 (기본 동작)
  3. Spring이 쿠키·헤더 비교 → 불일치면 403

csrf.disable() 복붙 금지

2회차의 disable은 Bearer만 받는 순수 API용. 쿠키 세션 BFF에서는 금지. SameSite=Lax는 보조 방어일 뿐.

BREACH 완화가 필요하면 Spring Security 문서의 SpaCsrfTokenRequestHandler(Xor 핸들러 + 평문 헤더 검증 조합)를 쓴다. 여기서는 구조를 보이기 위해 단순 핸들러를 사용.

로그아웃 — 앱 세션과 Keycloak SSO 세션을 함께 끊는다

@Bean   // BffSecurityConfig.java (추가)
SecurityFilterChain bff(HttpSecurity http,
                        ClientRegistrationRepository regs) throws Exception {
    var oidcLogout = new OidcClientInitiatedLogoutSuccessHandler(regs);
    oidcLogout.setPostLogoutRedirectUri("{baseUrl}");       // Keycloak 로그아웃 후 복귀
    http.logout(l -> l.logoutSuccessHandler(oidcLogout));  // 앱 세션 + Keycloak SSO 세션
    return http.build();                                     // (+ 앞 슬라이드의 설정)
}

앱 세션만 끊으면?

로그인 버튼을 누르면 SSO 세션 때문에 화면 없이 통과 → "로그아웃이 안 돼요".

  • FE는 form POST /logout + _csrf — fetch 금지 (302를 따라가야 함, 슬라이드 12)
  • Keycloak이 먼저 로그아웃시키면: Back-channel — .oidcLogout(o -> o.backChannel(…)) (6.2+)
id_token_hint는 세션에 보관한 ID 토큰. 그래서 BFF가 id_token도 들고 있었다(슬라이드 7). 공용 PC 환경이면 SSO 세션까지 끊는 것이 필수.

토큰 갱신 — FE는 모르고, BFF가 조용히 바꿔 끼운다

배치 — FE와 BFF를 같은 출처에 둔다

같은 출처면

  • CORS 설정 불필요
  • 쿠키 SameSite 문제 없음, withCredentials 불필요
  • Keycloak은 다른 출처여도 된다 — 리다이렉트로 다녀올 뿐 fetch하지 않는다

FE와 BFF 도메인이 다르면

CORS 허용 + SameSite=None; Secure + withCredentials — 피할 수 있으면 피한다.

개발 환경

Vite/webpack dev server의 proxy로 /api → localhost:8080. 같은 출처를 흉내 낸다.

04

자주 하는 실수

증상으로 먼저 만나고, 원인은 나중에 아는 것들

자주 하는 실수

❌ API에 302 응답

fetch가 로그인 HTML을 JSON으로 받는다. /api/**는 401로 분기.

❌ 403에 로그인 리다이렉트

SSO 세션이 즉시 되돌려 보내 무한 루프. 403은 안내만.

❌ csrf.disable() 복붙

쿠키 세션 BFF에서 끄면 다른 사이트가 사용자 브라우저로 요청을 보낼 수 있다.

❌ 토큰을 localStorage에

탭을 닫아도 남고 모든 스크립트가 읽는다. BFF에선 FE가 토큰을 볼 일 자체가 없다.

❌ 로컬 메모리 세션 + 인스턴스 2대

다른 인스턴스로 가면 로그아웃된 것처럼 보인다. Spring Session + Redis.

❌ 앱 세션만 로그아웃

Keycloak SSO 세션이 남아 화면 없이 재로그인. OidcClientInitiatedLogoutSuccessHandler.

⚠ BFF가 사용자 토큰 대신 자기 토큰으로 뒤쪽 API를 부른다

client credentials로 받은 BFF 자신의 토큰을 중계하면 사용자 role이 사라지고 모든 사용자가 BFF의 권한으로 실행된다. 반드시 세션의 사용자 토큰을 중계한다 — 4회차의 출발점.

에이전트 플랫폼과의 연결 — BFF는 사용자 토큰을 들고 있는 유일한 곳

BFF가 사용자 토큰을 그대로 들고 있기 때문에, 에이전트가 "사용자 대신" 부를 수 있는 재료가 생긴다. 그 재료를 어떻게 좁혀서(scope, aud) 넘기는지가 4회차.

BFF가 없고 SPA가 토큰을 들고 있어도 Token Exchange는 가능하다. 하지만 사용자 토큰이 브라우저에 노출된 채로 에이전트까지 흘러가면 공격면이 두 배가 된다. BFF가 "사용자 토큰의 단일 보관소"가 되는 것이 4회차 설계의 전제.

요약

  • 권한 판단은 BE에만. FE의 숨김은 편의.
  • 토큰은 서버(BFF)에, 브라우저엔 HttpOnly 쿠키만.
  • 페이지 요청은 302, API 요청은 401 + FE 인터셉터.
  • 401은 로그인으로, 403은 안내만 — 루프 방지.
  • oauth2Login() + EntryPoint 분기 = BFF의 뼈대.
  • 세션은 Redis, CSRF는 켜 둔 채 쿠키·헤더 방식.
  • 로그아웃은 Keycloak SSO 세션까지.
  • FE와 BFF는 같은 출처에.

다음 회차 — 4회차 A2A

에이전트는 누구로 API를 부르는가. 서비스 계정 / 패스스루 / Token Exchange, act 클레임, 멀티 에이전트의 scope·aud 최소화, MCP·A2A 프로토콜.

실습 과제

2회차의 Keycloak에 agent-portal confidential client를 만들고, oauth2Login() + 401 분기 설정으로 /api/me가 로그인 전 401, 후 200을 돌려주는지 확인한다.
