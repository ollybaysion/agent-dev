OIDC — 로그인한 사람이 누구인지 알기

OAuth 2.0 위의 신원 계층: ID Token · 표준 claim · Discovery · 로그아웃

대상: 보충 A(OAuth 2.0)를 본 에이전트 개발자 · 약 35분

이 자료의 위치 — OAuth 2.0이 답하지 않는 질문 하나

  • 보충 A의 결론: OAuth 2.0은 "이 앱이 무엇을 해도 되나"를 답한다
  • 그런데 SSO가 필요한 질문은 "지금 로그인한 사람이 누구인가"다
  • OAuth 2.0만으로 그걸 흉내 내면 뚫린다 (4번 슬라이드) — 그래서 2014년에 OpenID Connect가 그 위에 얹혔다
  • 끝나면: Spring 설정의 openid scope, issuer-uri, OidcUser가 규격의 어느 조각인지 읽힌다

한 문장 정의

OIDC = OAuth 2.0 흐름을 그대로 쓰되, 토큰 응답에 "누가 로그인했는지"를 서명해 담은 ID Token을 추가하고, 사용자 정보의 이름과 찾는 법을 표준화한 것.

구성 · 약 35분

용어 바꿔 읽기

Authorization Server → OP (OpenID Provider) · Client → RP (Relying Party) · Resource Owner → End-User. 역할은 같고 이름만 바뀐다.

1회차 10번(표준 지도)과 14번(토큰 3종)을 전제로 한다. 이 자료는 ID Token 하나를 끝까지 파고, 그 주변 장치(Discovery, UserInfo, 로그아웃)를 붙인다. Keycloak 콘솔에서 'OpenID Connect'라는 단어가 왜 모든 경로에 들어가는지가 끝나면 설명된다.
01

왜 OAuth 2.0만으로 로그인하면 안 되나

열쇠는 신분증이 아니다

시간 배분: 이 장 6분 (누적 8분).

문제 — Access Token은 열쇠지 신분증이 아니다

2013년까지 흔했던 "OAuth 로그인": access token을 받아 /userinfo를 불러 보고, 돌아온 사람으로 로그인 처리.

대상(aud)이 없다 — 어느 앱에 준 토큰인지 알 수 없어 바꿔치기가 된다

"로그인했다"는 사실이 없다 — 언제, 어떻게 인증했는지 토큰에 없다. 만료된 세션의 토큰도 통과

IdP마다 제각각 — 사용자 정보 주소·필드명이 전부 달라 코드가 IdP에 묶인다

이 공격은 2012년 실제로 여러 소셜 로그인 구현에서 발견됐다(토큰 바꿔치기, token substitution). 핵심 문장: "토큰이 진짜인 것과, 토큰이 나를 위한 것은 다르다." 보충 A의 aud 슬라이드와 연결된다.

해결 — OAuth 2.0 위에 "신원 계층"을 얹는다

  • 흐름은 그대로 — 같은 302, 같은 code, 같은 토큰 엔드포인트
  • 요청에 scope=openid를 넣으면 응답에 ID Token이 하나 더 온다
  • ID Token에는 누가(sub) · 누구에게(aud = 내 client_id) · 언제(auth_time) 로그인했는지가 서명돼 있다 → 바꿔치기 불가
  • 사용자 정보의 이름(claim)과 찾는 법(Discovery, UserInfo)이 표준 → IdP를 바꿔도 코드가 안 바뀐다
  • SSO에 꼭 필요한 로그아웃도 규격에 들어왔다 (OAuth 2.0엔 없다)

그래서 "Google로 로그인", "회사 SSO"는 전부 OIDC다. Keycloak 경로에 /protocol/openid-connect/가 들어가는 이유이기도 하다.

이 그림이 이 자료 전체의 지도다. 이후 슬라이드는 위층의 상자를 하나씩 연다: ID Token(02장), scope·claim·UserInfo·Discovery(03장), 로그아웃(04장).
02

ID Token

서명된 "로그인 영수증" — 무엇이 들어 있고, 무엇을 확인해야 하나

시간 배분: 이 장 12분 (누적 20분). 해부 4분, 검증 4분, Access Token과 비교 2분, sub 2분.

ID Token 해부 — Keycloak이 발급한 실제 payload

JWT payload (서명 생략)

{
  "iss": "https://kc.company.com/realms/company",
  "sub": "f3a1c2d4-7e8b-4a1f-9c2d-0b7e5f6a1234",
  "aud": "agent-portal",
  "exp": 1760000300,
  "iat": 1760000000,
  "auth_time": 1759999990,
  "nonce": "n-0S6_WzA2Mj",
  "azp": "agent-portal",
  "at_hash": "77QmUPtjPfzWtF2AnpK9RQ",
  "sid": "0a1b2c3d-…",
  "typ": "ID",
  "name": "김철수",
  "preferred_username": "kim",
  "email": "kim@company.com",
  "email_verified": true
}
claim뜻
iss · sub누가 발급했고 누구인가. 사용자의 전역 ID는 이 둘의 쌍
aud · azp누구에게 준 토큰인가 = 내 client_id. 4번 공격을 막는 칸
exp · iat만료 · 발급 시각 (초)
auth_time사용자가 실제로 로그인한 시각. SSO로 재사용되면 iat보다 훨씬 전
nonce로그인 요청 때 앱이 보낸 난수. 재전송 방지
at_hash함께 받은 access token의 해시. 토큰 쌍 바꿔치기 방지
sidOP의 세션 ID. 로그아웃 때 쓴다
name email …요청한 scope에 따라 붙는 프로필 claim

위 7줄(iss sub aud exp iat auth_time nonce)이 규격의 뼈대. 나머지는 scope와 OP 설정에 따라 달라진다. typ: "ID"는 Keycloak이 access token과 구분하려고 붙이는 것.

1회차 15번(JWT 해부)과 같은 형식이지만 이번엔 ID Token이다. aud가 API가 아니라 앱 자신(client_id)이라는 점을 손가락으로 짚는다. auth_time과 iat의 차이로 "SSO 세션 재사용"이 보인다는 것도 짚어 두면 3회차 세션 이야기가 쉬워진다.

RP가 ID Token을 받으면 확인하는 7가지 — Spring은 자동, 그래도 알아야 한다

  1. 서명 — iss의 JWKS 공개키로 검증. alg: none은 거부
  2. iss — 설정한 issuer와 문자열 완전 일치 (https · 포트 · 끝 슬래시까지)
  3. aud — 내 client_id가 들어 있어야 한다. 여러 개면 azp가 내 것이어야 한다
  4. exp · iat — 만료 전인지, 너무 옛날 발급은 아닌지. 시계 오차 ±60초 정도 허용
  5. nonce — 로그인 요청 때 세션에 둔 값과 일치. 캡처한 ID Token 재사용 차단
  6. at_hash — 같이 받은 access token의 해시와 일치 (토큰 응답에 둘이 함께 올 때)
  7. auth_time — max_age로 "N분 내 재인증"을 요구했을 때만 확인

Spring Security가 하는 것

oauth2Login() 경로에서 OidcIdTokenDecoderFactory가 1·2·4를, OidcIdTokenValidator가 3·5·(6)을 자동으로 한다. 실패하면 로그인 자체가 실패한다 — 사용자 객체가 만들어지지 않는다.

직접 짜지 말 것

"JWT 라이브러리로 디코딩해서 email만 꺼내 쓰면 되지"가 4번 공격의 재현이다. aud와 nonce를 빼먹는 순간 OAuth 2.0 시절로 돌아간다.

3번이 핵심. 다른 앱(A)용 ID Token은 aud가 A의 client_id라서 우리 앱(B)에서 바로 거절된다. 4번 슬라이드의 공격이 여기서 끝난다.

OpenID Connect Core 3.1.3.7절의 검증 목록을 7개로 추린 것이다. 질문이 많이 나오는 건 nonce: "code 흐름은 이미 state가 있는데 왜 또?" — state는 앱 세션과 콜백을 묶고, nonce는 ID Token 자체에 박혀 토큰 재전송을 막는다. 대상이 다르다.

한 줄 기억법

ID Token은 앱이 읽고 버리는 신분증, Access Token은 API에 내미는 열쇠.

1회차 14번 표를 ID/Access 둘로 좁혀 깊게 본 것. "그럼 refresh token은?"이 나오면 OIDC와 무관한 OAuth 2.0 장치라고 답하고 보충 A로 돌린다.

sub — 사용자를 식별하는 열쇠는 이메일이 아니다

❌ 이메일을 사용자 PK로

  • 이메일은 바뀐다 (결혼, 부서 이동, 도메인 변경)
  • 퇴사자 주소가 재할당되면 새 사람이 옛 계정을 연다
  • email_verified: false면 본인 소유인지도 모른다 — 일부 IdP는 미검증 이메일을 그대로 준다

✅ (iss, sub) 쌍을 PK로

  • sub는 OP가 보장하는 불변 · 재사용 없는 식별자. Keycloak은 사용자 UUID
  • 단, 그 issuer 안에서만 고유. IdP가 둘이면 iss까지 함께 저장
  • 이메일·이름은 표시용 속성으로 따로 저장하고 로그인 때마다 갱신

UserService.java — 로그인 후 내부 사용자와 연결

public AppUser onLogin(OidcUser oidc) {
    String iss = oidc.getIssuer().toString();
    String sub = oidc.getSubject();   // ← 열쇠
    String name = oidc.getFullName();
    String email = oidc.getEmail();

    return users.findByIssuerAndSubject(iss, sub)
        .map(u -> u.refreshProfile(name, email))
        .orElseGet(() -> users.save(
            AppUser.create(iss, sub, name, email)));
}

Pairwise sub

OP가 앱마다 다른 sub를 주는 옵션. 두 앱이 사용자 DB를 맞춰 봐도 같은 사람인지 모르게 한다. Keycloak은 Pairwise subject identifier mapper. 사내 SSO에선 보통 쓰지 않지만, 외부 파트너에 열 때 고려.

기존 시스템이 이메일을 PK로 쓰고 있으면 마이그레이션이 필요하다. 현실적인 중간 단계: 첫 OIDC 로그인 때 이메일로 기존 계정을 찾아 (iss, sub)를 붙여 두고, 이후부터는 sub로만 찾는다. 이 코드가 그 패턴이다.
03

scope · claim · UserInfo · Discovery

사용자 정보의 이름과 찾는 법을 표준화한 장치들

시간 배분: 이 장 10분 (누적 30분). scope→claim 3분, UserInfo 2분, Discovery 3분, response_type·nonce 2분.

Spring 설정의 그 줄

scope: openid, profile, email

openid가 스위치, 나머지는 "이름과 이메일도 달라". Spring은 openid가 있으면 OIDC 경로(OidcUser)로, 없으면 OAuth2 경로(OAuth2User)로 분기한다.

Keycloak에서는

이 표가 Client Scopes와 그 안의 Mapper로 구현돼 있다. roles 같은 회사 고유 claim은 OIDC 표준 밖 — 2회차에서 직접 만든다.

claim이 ID Token에 올지 UserInfo에 올지는 OP 설정에 따른다. Keycloak은 기본 둘 다. 그래서 "ID Token에 email이 없다"는 질문은 대개 Mapper의 'Add to ID token' 체크 문제.

보충 A의 scope(동작 범위)와 이 slide의 scope(정보 범위)가 같은 파라미터라는 점을 짚는다. OIDC는 OAuth 2.0의 scope 칸을 빌려 "어떤 정보를 달라"는 뜻으로 쓴다. 한 요청에 둘을 섞어 보낼 수 있다: scope=openid email accounts:read.

UserInfo 엔드포인트 — ID Token에 다 못 담은 정보를 가져오는 곳

access token으로 부른다 (ID Token이 아니다)

규칙 하나: 응답의 sub가 ID Token의 sub와 다르면 버린다. 토큰 바꿔치기의 마지막 방어선. Spring이 확인한다.

언제 쓰나

  • ID Token을 작게 유지하고 싶을 때 — 프로필 사진 URL, 주소 같은 큰 값
  • OP가 특정 claim을 ID Token에 안 넣도록 설정돼 있을 때
  • 로그인 이후 바뀐 정보를 다시 읽을 때 (ID Token은 발급 시점 스냅샷)

Spring은 자동으로 부른다

OidcUserService가 로그인 직후 1회 호출 — 조건: Discovery에 userinfo_endpoint가 있고, access token의 scope에 profile email address phone 중 하나라도 있을 때. 결과는 ID Token claim과 합쳐져 OidcUser.getClaims()에 들어간다.

매 요청마다 부르는 곳이 아니다. 로그인 때 한 번 읽어 세션에 둔다. 사용자 정보가 매 요청 필요하면 그건 세션의 일이다.

"ID Token이 있는데 UserInfo는 왜 있냐"는 질문의 답은 '크기와 시점'이다. 그리고 4번 공격을 다시 상기: UserInfo만으로 로그인 판단을 하면 안 되는 이유는 UserInfo가 aud를 확인하지 않기 때문이다. ID Token 검증을 통과한 뒤의 보조 수단일 뿐이다.

Discovery — issuer 주소 하나로 나머지를 전부 알아낸다

GET {issuer}/.well-known/openid-configuration

{
  "issuer": "https://kc.company.com/realms/company",
  "authorization_endpoint": "{issuer}/protocol/openid-connect/auth",
  "token_endpoint": "{issuer}/protocol/openid-connect/token",
  "userinfo_endpoint": "{issuer}/protocol/openid-connect/userinfo",
  "end_session_endpoint": "{issuer}/protocol/openid-connect/logout",
  "jwks_uri": "{issuer}/protocol/openid-connect/certs",
  "scopes_supported": ["openid", "profile", "email", "roles", …],
  "response_types_supported": ["code", "id_token", …],
  "code_challenge_methods_supported": ["plain", "S256"],
  "backchannel_logout_supported": true
}

실제 문서에는 {issuer} 자리에 전체 URL이 반복된다. 줄여 적은 것.

Spring의 issuer-uri 한 줄이 하는 일

기동 시 이 문서를 1회 받아 authorize · token · userinfo · logout 주소와 jwks_uri를 채운다. 공개키는 캐시하고 모르는 kid가 오면 다시 받는다 — 키 회전이 무중단인 이유. 이 문서가 없는 순수 OAuth 2.0 서버(GitHub 등)는 주소를 손으로 적는다.

두 가지 함정

  • 기동 때 OP가 응답하지 않으면 앱이 뜨지 않는다
  • issuer는 토큰의 iss와 글자 단위로 같아야 한다. 프록시 뒤 Keycloak은 KC_HOSTNAME을 안 맞추면 http://localhost:8080으로 발급해 전부 실패
1회차 16번(Discovery와 JWKS)을 RP 관점에서 다시 본다. Keycloak 실습(2회차)에서 가장 많이 겪는 장애가 iss 불일치다. 이 슬라이드의 warn 카드를 2회차 트러블슈팅에서 다시 보여준다.

code id_token …HybridID Token은 즉시, access는 code로특수 용도. 쓰지 않는다

그런데 왜 code 흐름에도 nonce가 있나

nonce는 원래 Implicit에서 fragment로 날아오는 ID Token의 재전송을 막으려고 생겼다. code 흐름에선 토큰이 백 채널로 오지만, Spring과 OP는 그래도 넣는다 — 비용이 0이고, ID Token 자체에 박히는 유일한 요청-응답 묶음이기 때문. state는 세션과 콜백을, nonce는 세션과 ID Token을 묶는다.

로그인 요청에 더 붙일 수 있는 것 (OIDC 추가 파라미터)

  • prompt=login — SSO 세션이 있어도 다시 로그인 화면 (민감 작업 전)
  • prompt=none — 화면 없이 세션 확인만. 없으면 login_required 오류
  • max_age=300 — 5분 내 인증이 아니면 재인증. auth_time으로 확인
  • login_hint=kim@company.com — 아이디 칸 미리 채우기
  • ui_locales=ko — 로그인 화면 언어
Spring에서 prompt나 max_age를 붙이려면 OAuth2AuthorizationRequestResolver를 커스터마이즈한다. A2A 자료의 '사람 승인 게이트'에서 prompt=login과 max_age를 실제로 쓴다.
04

세션과 로그아웃

로그인은 한 곳, 세션은 두 개 — 로그아웃도 두 번

시간 배분: 이 장 7분 (누적 37분, 요약 포함). 로그아웃 3분, Spring 매핑 2분, 실수·요약 2분.

로그아웃 — RP-Initiated Logout과 세션 두 개

  1. 브라우저 → 앱 POST /logout (CSRF 토큰 포함, fetch 금지)
  2. 앱이 자기 세션을 지우고 302 → OP end_session_endpoint + id_token_hint · post_logout_redirect_uri
  3. OP가 SSO 세션을 지운다 — id_token_hint로 누구인지 확인
  4. OP가 302 → post_logout_redirect_uri. 등록된 주소만

앱 세션만 지우면

다음 클릭에 302 → OP → SSO 세션이 살아 있어 화면 없이 자동 재로그인. "로그아웃이 안 된다"는 증상.

Back-Channel Logout (반대 방향)

OP 쪽에서 세션이 끊기면 OP가 각 앱에 직접 logout_token(sid 포함)을 POST, 앱이 그 세션을 지운다. Spring 6.2+ oidcLogout().

SecurityConfig.java

@Bean
SecurityFilterChain filterChain(HttpSecurity http,
        ClientRegistrationRepository clients)
        throws Exception {
    http
        .oauth2Login(Customizer.withDefaults())
        .logout(l -> l.logoutSuccessHandler(
            oidcLogout(clients)));          // ← 2·3·4
    return http.build();
}

LogoutSuccessHandler oidcLogout(
        ClientRegistrationRepository clients) {
    var h = new OidcClientInitiatedLogoutSuccessHandler(
        clients);
    // Keycloak Client에 등록된 주소여야 한다
    h.setPostLogoutRedirectUri("{baseUrl}/");
    return h;
}

Keycloak Client의 Valid post logout redirect URIs에 실제 주소를 넣지 않으면 "Invalid redirect uri".

3회차 BFF 로그아웃 슬라이드와 같은 흐름을 규격 이름으로 부른 것. OAuth 2.0에는 로그아웃 규격이 없다는 사실을 강조 — 이것도 OIDC가 얹은 것이다.

Spring Security에 대응시키기 — 규격 용어 → 클래스

MeController.java

@GetMapping("/api/me")
Map<String, Object> me(
    @AuthenticationPrincipal OidcUser user) {
    var id = user.getIdToken();
    return Map.of(
        "sub",      user.getSubject(),
        "name",     user.getFullName(),
        "email",    user.getEmail(),
        "authTime", id.getAuthenticatedAt(),
        "claims",   user.getClaims());
}
// claims = ID Token + UserInfo 합본

OidcUser는 OAuth2User를 상속한다. 컨트롤러에 OAuth2User로 받아도 동작하지만 getIdToken()이 없다. OIDC로 로그인했으면 OidcUser로 받는다.

1회차 20번(로그인 후 사용자 정보)의 코드가 왜 OidcUser인지가 여기서 설명된다. GitHub 로그인처럼 openid가 없는 OP를 붙일 때만 마지막 줄의 OAuth2User 경로를 쓴다.

자주 하는 실수

❌ access token으로 로그인 판단

UserInfo가 kim을 돌려줬다고 kim으로 로그인시킨다. 4번 슬라이드의 공격. 로그인 판단은 aud가 검증된 ID Token으로만.

❌ ID Token을 API에

aud가 client_id라 API에서 401. 거꾸로 API가 ID Token을 받아 주도록 고치면 더 나쁘다 — 로그인 영수증이 열쇠가 된다.

❌ 이메일을 사용자 PK로

바뀌고, 재할당되고, 미검증일 수 있다. (iss, sub)로 찾고 이메일은 속성으로.

❌ JWT 라이브러리로 직접 검증

서명만 보고 aud · nonce · iss를 빼먹는다. oauth2Login()이 하는 7가지를 손으로 다시 짜지 말 것.

❌ iss 불일치를 설정으로 덮기

프록시 뒤 Keycloak이 http://localhost로 발급하는데 검증을 끈다. 고칠 곳은 KC_HOSTNAME이다.

❌ 앱 세션만 로그아웃

다음 클릭에 자동 재로그인. end_session_endpoint로 보내고, post logout URI를 Keycloak에 등록.

1회차·보충 A의 실수와 겹치지 않는 '신원' 쪽 실수만 모았다. 첫 번째와 네 번째가 같은 뿌리(검증 생략)다.

요약 · 본편으로

  • Access Token은 열쇠, ID Token은 신분증 — 열쇠로 신원을 판단하면 바꿔치기에 뚫린다
  • OIDC = OAuth 2.0 흐름 + scope=openid + 서명된 ID Token + 표준 claim + Discovery + 로그아웃
  • ID Token의 aud = 내 client_id, nonce, iss, exp, 서명 — Spring이 7가지를 자동 검증
  • 사용자의 열쇠는 (iss, sub). 이메일은 속성
  • profile email은 claim 묶음 이름. 큰 값은 UserInfo로
  • issuer 주소 하나 → Discovery → 나머지 자동. iss는 글자 단위 일치
  • 세션은 둘 — 로그아웃은 end_session_endpoint까지

본편에서 이어지는 곳

2회차 Keycloak의 Client Scopes · Mapper가 이 자료의 claim 표를 구현한다. 3회차 ID Token으로 만든 세션을 BFF가 들고, access token만 API로. 별도 A2A 에이전트가 "kim 대신" 일할 때 ID Token의 sub를 어떻게 끝까지 가져가나.
