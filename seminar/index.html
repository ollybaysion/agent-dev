SSO → Keycloak → BFF. Java/Spring 경험은 있지만 SSO·IdP·OAuth를 처음 다루는 에이전트 개발 실무자를 위한 시리즈입니다. 매 회차는 왜 필요한가 → 개념(그림) → Spring 코드 → 자주 하는 실수 → 다음 회차 순서로 진행합니다.

들어가며 · 약 15분 · 사전 지식 없음

놀이공원으로 이해하는 인증·인가

손님, 매표소, 놀이기구, 심부름 로봇, 안내 데스크. 다섯 등장인물로 시리즈 전체(SSO·Keycloak·BFF·OAuth 2.0·OIDC·A2A)를 먼저 지나간 뒤, 장마다 문장 하나와 그림 하나뿐이고, 마지막에 이름표만 붙입니다. 시리즈를 처음 보는 분은 여기서 시작하세요.

  • 매표소 하나와 손목밴드 (SSO) · 사서 설치하는 부스 (Keycloak)
  • 쿠폰 (OAuth 2.0) · 명찰 (OIDC) · 입구 직원의 세 가지 검사 (Resource Server)
  • 손목이냐 안내 데스크냐 (BFF) · 친구의 친구 (A2A)

회차

1회차

SSO — 로그인을 한 곳에 맡기기

서비스마다 로그인을 만들던 방식에서 벗어나, 신원 제공자(IdP) 한 곳을 믿는 구조로.

  • 인증(누구냐)과 인가(무엇을 할 수 있냐)의 구분, 401과 403
  • OAuth 2.0 · OIDC · Authorization Code 흐름, 프런트/백 채널
  • JWT 해부와 서명 검증, 세션 vs 토큰
  • Spring oauth2Login()으로 로그인 화면 코드 0줄
슬라이드 열기
2회차

Keycloak — IdP를 직접 운영하기

Realm, Client, Role, Scope, Mapper가 토큰 안의 어떤 값이 되는지, Spring이 그 토큰을 어떻게 검증하는지.

  • 핵심 객체 지도와 관리 콘솔 설정 순서
  • 토큰 발급 두 경로: 사용자(code) vs 에이전트(client credentials)
  • Spring Resource Server: roles 변환기, aud 검증기
  • 에이전트용 Service Account 만들고 토큰 받기

3회차

BFF — 토큰을 브라우저에 두지 않기

FE/BE가 나뉘었을 때 토큰은 누가 들고 있어야 하나. SPA+PKCE와 BFF를 비교하고 BFF를 Spring으로 만든다.

  • 페이지 요청은 302, API 요청은 401 — 왜 다르게 응답하나
  • FE 최소 작업: 인터셉터 하나, 401/403 무한 루프 피하기
  • 세션(Redis) · CSRF · 로그아웃 · 토큰 갱신 · 같은 출처 배치
  • Spring Cloud Gateway TokenRelay

보충 A · 약 35분

OAuth 2.0 — 권한을 빌려주는 규칙

비밀번호를 넘기지 않고 범위·대상·기한이 있는 토큰을 빌려주는 인가 프레임워크. 답하는 질문: "이 앱이 무엇을 해도 되나".

  • 왜 생겼나 — 제3자 앱에 비밀번호를 주던 시절의 문제
  • 승인 방식 지도: Code+PKCE · Client Credentials · Refresh, 폐기된 Implicit·Password와 OAuth 2.1
  • Bearer의 의미, opaque vs JWT, scope는 "무엇을" aud는 "어디에"
  • state · PKCE · redirect_uri · Client 두 종류, Spring 설정 키 대응표
슬라이드 열기
보충 B · 약 35분

OIDC — 로그인한 사람이 누구인지 알기

OAuth 2.0 위에 얹은 신원 계층. 답하는 질문: "지금 로그인한 사람이 누구인가".

  • 왜 access token으로 로그인하면 뚫리나 — 토큰 바꿔치기
  • ID Token 해부와 7가지 검증, ID vs Access, 사용자 열쇠는 (iss, sub)
  • 표준 scope·claim · UserInfo · Discovery · response_type과 nonce
  • RP-Initiated / Back-Channel Logout, OidcUser 대응표

별도 · 약 50분 · 전제: 1~3회차

A2A — 에이전트 간 인증과 위임

에이전트가 API를 부를 때 "누구"로 부르는가. 사용자 정체성을 잃지 않고 최소 권한으로 위임하는 방법. 본 시리즈의 결론(SSO · Keycloak · BFF)을 전제로 하지만, 인증·인가의 기본 흐름과는 별개의 주제라 따로 둔다.

  • 위임 모델 A/B/C: 서비스 계정, 패스스루, Token Exchange
  • act 클레임과 위임 체인, 멀티 에이전트의 scope/aud 최소화
  • MCP 서버 인증(OAuth 2.1)과 A2A 프로토콜의 Agent Card
  • 감사 로그, 사람 승인 게이트, 프롬프트 인젝션을 권한으로 막기

사전 준비

개발 환경

  • JDK 17 이상, Spring Boot 3.x (Spring Security 6.x)
  • Docker Desktop (Keycloak 실습용)
  • HTTP 클라이언트: curl 또는 IntelliJ HTTP Client

Keycloak 실습 서버 (2회차부터)

docker run --name kc -p 8180:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:26.4 start-dev
# 관리 콘솔: http://localhost:8180  (실습 전용 설정. 운영은 start-dev 금지)
