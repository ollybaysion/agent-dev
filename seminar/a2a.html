A2A — 에이전트 간 인증과 위임

에이전트는 누구로 API 를 부르는가

대상: Java/Spring 경험이 있는 에이전트 개발자 · 전제: 1~3회차(SSO · Keycloak · BFF) · 50분

1~3회차 복습과 오늘의 목표

1회차 · SSO

로그인은 IdP 한 곳에서. 앱은 서명된 JWT 만 검증한다.

2회차 · Keycloak

Role 은 Keycloak DB → Protocol Mapper → JWT 의 realm_access.roles. Spring 은 Resource Server + @PreAuthorize.

3회차 · BFF

사용자 토큰은 서버(BFF) 가 보관. 브라우저엔 HttpOnly 쿠키만. BFF 가 뒤쪽 API 로 Bearer 를 중계한다.

오늘의 목표

  1. 에이전트가 API 를 부를 때 토큰이 누구 것인지 말할 수 있다
  2. 위임 모델 A/B/C 를 구분하고 Token Exchange 를 Spring 으로 구현한다
  3. MCP · A2A 프로토콜에서 인증이 어디에 끼어드는지 안다

이번 회차의 질문은 하나다.
"에이전트는 누구로 API 를 부르는가?"

3회차 마지막에 던진 질문을 그대로 이어받는다. 참석자가 2회차의 roles 변환기 코드를 기억하는지 먼저 확인하면 뒤의 코드 슬라이드가 쉬워진다.

문제: 토큰이 누구 것인가

2회차 Q&A 에서 나온 질문("Service 계층에서 role 을 알 수 있나")의 답이 "토큰 주인의 role" 이었다. 에이전트 구조에서는 토큰 주인이 사람이 아닐 수 있다는 것이 오늘의 출발점.

프롬프트 인젝션: 권한이 마지막 방어선

  • LLM 은 읽은 문서 속 지시에 속을 수 있다 (prompt injection)
  • 프롬프트 방어는 확률적. 100% 를 보장하지 못한다
  • 그러나 토큰에 없는 권한은 LLM 이 만들어 낼 수 없다
  • API 가 scope · aud 를 검사하면 속은 호출도 거절된다

설계 원칙

에이전트의 토큰은 그 작업에 필요한 만큼만. 읽기 작업에 쓰기 scope 를 주지 않는다.

세 가지 위임 모델

A 구현은 쉽다(2회차 client credentials). 대신 누가 시켰는지 사라진다.

B aud 불일치, 에이전트 기록 없음, 사용자 전권 노출. RFC 8693 이 이 문제를 풀려고 나왔다.

C 사용자(sub) 와 에이전트(act) 가 한 토큰에. 대상·범위도 좁힌다.

세 모델을 한 장에서 보여 주고, 다음 두 장에서 A/B 의 한계와 C 의 흐름을 깊게 본다. "B 가 왜 안 되나" 를 참석자에게 먼저 물어보면 좋다.

모델 A 와 B — 언제 쓰고, 왜 안 되나

A 서비스 계정 (client credentials)

적합한 경우

  • 사용자와 무관한 작업: 야간 배치, 외부 데이터 수집, 모니터링
  • 구현은 2회차 그대로 — client_id + secret 으로 토큰

사용자 요청 처리에 쓰면

  • 모든 사용자가 에이전트 권한으로 승격된다
  • 감사 로그에 사용자가 없다 — 누가 시켰는지 모른다
  • 에이전트가 늘면 "admin SA 하나 공유" 로 흐르기 쉽다

B 사용자 토큰 패스스루

사용자 토큰을 손대지 않고 뒤쪽 API 로 그대로 전달한다.

  • aud 불일치: 플랫폼용 토큰을 report-api 가 받는다. 제대로 검증하면 거절, 안 하면 구멍
  • 에이전트 기록 없음: 사람이 직접 한 것처럼 보인다
  • 수명 종속: 긴 에이전트 작업 중 사용자 토큰이 만료된다
  • 최소 권한 위반: 사용자의 모든 권한이 에이전트에 넘어간다

결론: 쓰지 말 것. 다음 장의 C 가 이 네 가지를 모두 해결한다.

모델 C — Token Exchange (RFC 8693)

③ 의 요청은 report-agent 가 자기 client 자격으로 한다. 즉 "누가 교환을 요청하는가" 도 Keycloak 이 안다. 그래서 정책에서 "이 client 가 이 audience 로 교환 가능한가" 를 걸 수 있다.

교환 요청과 응답

요청 (본문은 실제로는 한 줄 form)

POST /realms/company/protocol/openid-connect/token HTTP/1.1
Host: kc.company.com
Authorization: Basic base64(report-agent:secret)   # client 인증
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=eyJhbGciOi...     # 사용자 kim 의 access token
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&audience=report-api
&scope=report:write

응답

{
  "access_token": "eyJhbGciOi...",
  "token_type": "Bearer",
  "expires_in": 300,
  "issued_token_type": "urn:ietf:params:oauth:token-type:access_token"
}

응답 access_token 의 payload (디코딩)

{
  "iss": "https://kc.company.com/realms/company",
  "sub": "kim",
  "azp": "report-agent",
  "aud": "report-api",
  "scope": "report:write",
  "act": { "azp": "report-agent" },
  "exp": 1760000300
}

읽는 법

  • sub 는 그대로 kim — 누구 대신인가
  • act 는 report-agent — 누가 실제로 부르나
  • aud · scope · exp 는 최소로, 짧게
act 는 RFC 8693 의 위임(delegation) 형식이다. Keycloak 표준 교환은 sub 를 사용자, azp 를 요청 client 로 발급한다. act 클레임이 기본으로 들어가는지는 버전별로 확인하고, 없으면 매퍼로 넣는다. 발표 때 이 점을 단정하지 말 것.

act 클레임과 위임 체인

두 번째 교환 후 payload

{
  "sub": "kim",
  "aud": "report-api",
  "scope": "report:write",
  "azp": "report-agent",
  "act": {
    "azp": "report-agent",
    "act": { "azp": "orchestrator" }
  },
  "exp": 1760000300
}

sub 는 끝까지 kim. 체인이 길어져도 사용자 정체성은 잃지 않는다.

멀티 에이전트: 토큰을 에이전트별로 좁힌다

"토큰 하나로 다 돌리면 편한데요" 라는 반응이 흔하다. 그 편함이 곧 앞 장의 프롬프트 인젝션 피해 범위라는 점을 연결해서 설명한다.

Keycloak 설정 — 교환을 허용하기

  1. 대상 client 만들기: report-api — 토큰의 aud 가 될 이름. 로그인은 하지 않는다.
  2. Client scope 정의: report:write 등. report-api 용 Audience 매퍼를 포함시킨다.
  3. 요청 client report-agent: Client authentication ON (secret 발급), Capability config 에서 Standard token exchange ON.
  4. report-agent 에 교환할 scope 를 할당 — 요청한 scope 는 이 client 에 허용된 것만 통과한다.
  5. curl 로 교환해 보고 응답 토큰을 디코딩해 aud · scope · sub 확인.

버전 주의

Standard token exchange 는 Keycloak 26.2+ 정식 기능. 그 이전은 preview(--features=token-exchange) 와 세부 권한 정책이 필요했다.

허용 범위를 좁게

교환은 "어떤 client 가 어떤 audience 로" 를 묻는 기능이다. 모든 client 에 켜 두면 모델 B 와 다를 게 없다.

실습 토큰만 디코더에 붙일 것. 운영 토큰은 외부 사이트에 올리지 않는다. cut -d. -f2 | base64 -d 면 충분하다.

오케스트레이터 ① 선언형 설정

application.yml

spring:
  security:
    oauth2:
      client:
        provider:
          keycloak:
            issuer-uri: https://kc.company.com/realms/company
        registration:
          report-api-exchange:              # 교환용 등록
            provider: keycloak

            authorization-grant-type: >-
              urn:ietf:params:oauth:grant-type:token-exchange

무엇이 다른가

authorization-grant-type 이 교환 grant. Spring Security 6.3+ 가 이 값을 알아듣는다.

대상 API 마다 등록을 하나씩 둔다: search-api-exchange, storage-api-exchange… scope 가 각각 다르다.

audience 는 yml 로 못 넣는다. 다음 장에서 파라미터 변환기로 추가한다.

오케스트레이터 ② Manager 와 RestClient

@Bean
OAuth2AuthorizedClientManager clientManager(
        ClientRegistrationRepository regs,
        OAuth2AuthorizedClientRepository repo) {
    var rc = new RestClientTokenExchangeTokenResponseClient();
    rc.addParametersConverter(req -> MultiValueMap.fromSingleValue(
            Map.of("audience", "report-api")));        // + audience (6.4+)
    var exchange = new TokenExchangeOAuth2AuthorizedClientProvider();
    exchange.setAccessTokenResponseClient(rc);
    var manager = new DefaultOAuth2AuthorizedClientManager(regs, repo);
    manager.setAuthorizedClientProvider(
            OAuth2AuthorizedClientProviderBuilder.builder()
                    .provider(exchange).build());
    return manager;
}
@Bean
RestClient reportApi(OAuth2AuthorizedClientManager manager) {
    var oauth = new OAuth2ClientHttpRequestInterceptor(manager);   // 6.4+
    oauth.setClientRegistrationIdResolver(r -> "report-api-exchange");
    return RestClient.builder().baseUrl("https://report-api")
            .requestInterceptor(oauth).build();
}

흐름

  • reportApi.post()… 를 부르면
  • 인터셉터가 manager 에게 토큰을 요청
  • manager 가 현재 SecurityContext 의 사용자 Jwt 를 subject_token 으로 교환 (기본 resolver)
  • 결과를 Authorization: Bearer 로 붙인다

호출하는 코드에는 토큰 관련 줄이 0줄. 교환·캐시·만료 처리 모두 manager 몫.

6.3 에서 TokenExchangeOAuth2AuthorizedClientProvider 가, 6.4 에서 RestClient 용 인터셉터와 RestClient 기반 응답 클라이언트가 들어왔다. 그 이전 버전이면 WebClient 의 ServerOAuth2AuthorizedClientExchangeFilterFunction 을 쓰거나 다음 장처럼 직접 POST 한다.

오케스트레이터 ③ 직접 POST (이해용)

@Service
public class TokenExchangeClient {
    static final String GRANT =
            "urn:ietf:params:oauth:grant-type:token-exchange";
    static final String TOKEN_TYPE =
            "urn:ietf:params:oauth:token-type:access_token";
    // kc: RestClient(https://kc.company.com), secret: 주입된 client secret

    public String exchangeFor(String audience, String scope) {
        Jwt userJwt = (Jwt) SecurityContextHolder.getContext()
                .getAuthentication().getPrincipal();    // 사용자 토큰
        var form = new LinkedMultiValueMap<String, String>();
        form.add("grant_type", GRANT);
        form.add("subject_token", userJwt.getTokenValue());
        form.add("subject_token_type", TOKEN_TYPE);
        form.add("audience", audience);
        form.add("scope", scope);
        return kc.post()
                .uri("/realms/company/protocol/openid-connect/token")
                .headers(h -> h.setBasicAuth("report-agent", secret))
                .contentType(MediaType.APPLICATION_FORM_URLENCODED)
                .body(form)
                .retrieve().body(TokenResponse.class).accessToken();
    }
}

앞 장과 같은 일

HTTP 로 보면 교환은 form POST 한 번이다. 8장의 요청을 코드로 옮긴 것.

운영에서는 ② 를

이 코드는 캐시도 만료 처리도 없다. 매 호출마다 Keycloak 을 두드린다.

TokenResponse 는 access_token 만 받는 record. 응답의 expires_in 을 보고 캐시 여부를 정한다.

업무 API — act 읽기와 감사 로그

@RestController
public class ReportController {

    @PostMapping("/reports")
    @PreAuthorize("hasAuthority('SCOPE_report:write')")  // 교환된 scope
    public ReportDto create(@RequestBody ReportRequest req,
                            @AuthenticationPrincipal Jwt jwt) {
        String user = jwt.getSubject();                  // kim — 누구 대신
        Map<String, Object> act = jwt.getClaim("act");    // 누가 대신
        String actor = act == null ? "(직접)" : chain(act);
        audit.log("report.create", user, actor);         // kim / 경로
        return reportService.create(req, user);
    }

    @SuppressWarnings("unchecked")
    private static String chain(Map<String, Object> act) {
        String azp = String.valueOf(act.get("azp"));
        if (!(act.get("act") instanceof Map<?, ?> inner)) return azp;
        return azp + " via " + chain((Map<String, Object>) inner);
    }
}

달라진 점은 두 줄

2회차 Resource Server 설정은 그대로. act 를 읽어 감사 로그에 남기는 것만 추가.

scope 권한

기본 변환기는 scope 를 SCOPE_ 권한으로 만든다. 2회차의 roles 변환기로 바꿨다면 두 결과를 합쳐서 반환해야 한다.

데이터 소유 검사("이 보고서가 kim 것인가") 는 여전히 user 기준. 에이전트가 끼어도 바뀌지 않는다.

감사 로그의 세 칼럼: 무엇을, 누구 대신, 누가(경로). 사고 조사 때 "에이전트가 했다" 로 끝나지 않으려면 act 체인이 있어야 한다.

@Bean("agentExecutor")
AsyncTaskExecutor agentExecutor() {
    var p = new ThreadPoolTaskExecutor();
    p.setThreadNamePrefix("agent-");
    p.initialize();
    return new DelegatingSecurityContextAsyncTaskExecutor(p);
}

✅ 방법 2 — 필요한 값을 명시적으로 넘긴다 (권장)

String subject = userJwt.getTokenValue(); // 요청 스레드에서
agentExecutor.submit(() ->
        runAgent(req, subject));          // 작업 스레드엔 값으로

에이전트 작업은 오래 걸린다

  • 요청 스레드가 끝나면 ThreadLocal 도 사라진다 — 방법 1 은 짧은 작업용
  • 작업 중 사용자 토큰이 만료되면 교환도 실패 → 작업 시작 시 필요한 토큰을 먼저 교환해 두거나, 만료 시 재교환 경로를 둔다
  • 큐·워커 구조라면 메시지에 subject_token 대신 교환된 토큰을 싣는다 (범위가 좁다)

04

MCP 와 A2A

도구 연결과 에이전트 연결 — 인증은 어디에 끼어드는가

MCP 서버 인증 — 도구도 Resource Server

  • MCP(Model Context Protocol): 모델이 도구·데이터에 붙는 표준. 인증 사양(2025-06)은 OAuth 2.1
  • MCP 서버는 그냥 Resource Server — 2회차와 같은 JWT 검증
  • 401 의 WWW-Authenticate 가 메타데이터 위치를 알려준다 (RFC 9728)
  • 인가 서버(Keycloak) 정보는 /.well-known/oauth-protected-resource 에서
  • PKCE 필수, resource 파라미터(RFC 8707)로 토큰의 aud 를 그 MCP 서버로 고정
  • 동적 클라이언트 등록(RFC 7591) 권장 — 에이전트가 사전 등록 없이 client 가 된다
사내 MCP 서버를 Spring 으로 만든다면 설정은 2회차 Resource Server + aud 검증기와 동일하다. 추가로 RFC 9728 메타데이터 엔드포인트 하나와 401 응답의 WWW-Authenticate 헤더만 더 내면 된다.

A2A 프로토콜 — 에이전트끼리 일을 주고받기

  • A2A(Agent2Agent): 에이전트 간 상호운용 공개 프로토콜. Google 2025.4 공개 → 2025.6 Linux Foundation 이관
  • Agent Card: 원격 에이전트의 명함 — 이름, skills, 입출력, 인증 방식
  • Task: 작업 단위. 상태 머신으로 진행 (submitted → working → … → completed)
  • Message / Artifact: 주고받는 메시지와 결과물. SSE 로 진행 상황 스트리밍
  • 전송: JSON-RPC 2.0 over HTTP(S) — message/send, message/stream, tasks/get. v0.3 부터 gRPC · HTTP+JSON 도
  • 인증은 프로토콜 밖 HTTP 계층 — 즉 Bearer JWT. 우리 Keycloak 그대로

에이전트 권한 설계 원칙

최소 권한

scope · aud 를 에이전트별 · 작업별로. 읽기 작업에 쓰기 scope 를 주지 않는다.

짧은 수명

교환된 토큰은 5~15분. 긴 작업은 재교환. 탈취돼도 피해 창이 짧다.

사용자 정체성 유지

sub 는 사용자, 에이전트는 act. 서비스 계정 토큰으로 사용자 요청을 처리하지 않는다.

감사 로그

무엇을 · 누구 대신 · 누가(act 체인). 사고 조사가 "에이전트가 했다" 로 끝나지 않게.

사람 승인 게이트

고위험 작업(삭제, 송금, 배포)은 scope 를 처음부터 주지 않고 승인 후 발급. A2A 의 input-required 가 이 자리.

토큰을 모델에게 주지 않기

토큰은 프롬프트 · LLM 컨텍스트 · 로그에 넣지 않는다. 호출은 코드(인터셉터)가 붙인다.

자주 하는 실수

❌ admin 서비스 계정 하나를 공유

모든 에이전트 · 모든 서브에이전트가 같은 토큰. 프롬프트 인젝션 한 번이 전사 권한이 된다.

❌ 사용자 토큰 패스스루

aud 불일치, 에이전트 기록 없음, 사용자 전권 노출. 모델 B 다.

❌ act 를 기록하지 않음

토큰에 있어도 로그에 안 남기면 없는 것. 감사 로그 칼럼을 먼저 설계한다.

❌ 토큰을 프롬프트 · 로그에

"이 토큰으로 호출해" 라고 모델에게 주면 출력 · 로그 · 추적 데이터로 샌다.

❌ 교환 정책 전면 허용

모든 client 가 모든 audience 로 교환 가능하면 Keycloak 이 토큰 복사기가 된다.

❌ 비동기에서 SecurityContext 유실

@Async 스레드에서 null. 전파 Executor 를 쓰거나 값을 명시적으로 넘긴다.

시리즈 전체 요약 — 한 장의 아키텍처

1 · SSO 로그인은 IdP 한 곳, 앱은 서명된 JWT 만 검증

2 · Keycloak Role → 매퍼 → JWT. Spring 은 Resource Server + aud 검증

3 · BFF 토큰은 서버에, 브라우저엔 쿠키. API 는 401, 페이지는 302

A2A (별도) 사용자(sub) + 에이전트(act) 를 교환 토큰에. aud · scope 는 최소로
