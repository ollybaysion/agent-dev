에이전트 개발자를 위한 인증·인가 세미나 · 1회차

SSO — 로그인을 한 곳에 맡기기

인증의 기초: IdP, OIDC, JWT

대상: Java/Spring 경험이 있는 에이전트 개발자 · 사전 지식: SSO 없음 · 50분

시리즈 지도 — 3회차의 흐름, 그리고 별도 자료

이 시리즈가 다루는 것

사람과 에이전트가 누구인지 증명하고, 허락된 것만 하게 만드는 구조. 전부 Spring으로 구현한다.

다루지 않는 것

암호학 이론, Keycloak 운영(HA·백업), LDAP/AD 연동 세부, 모바일 앱 인증.

세 회차는 독립 강의가 아니라 한 줄기다. 1회차에서 "토큰을 받는 법"을, 2회차에서 "토큰에 무엇이 들어가고 어떻게 검증하는지"를, 3회차에서 "브라우저가 있을 때 토큰을 어디 둘지"를 다룬다. "에이전트가 남을 대신해 부를 때"는 이 흐름을 전제로 하는 별도 자료 A2A에서 따로 다룬다.

오늘의 목표

  1. 인증과 인가를 구분해서 말할 수 있다 — 401과 403이 왜 다른지
  2. Authorization Code 흐름을 그림 없이 설명할 수 있다 — 왜 code를 거치는지, 토큰 3종이 각각 어디로 가는지
  3. Spring Boot 앱에 SSO 로그인을 붙일 수 있다 — 로그인 화면 코드 0줄로

전제

Spring MVC, Filter, 세션 쿠키는 안다. SSO·OAuth·IdP·JWT는 처음이라고 가정한다.

진행

① 왜 필요한가 → ② 개념(그림) → ③ Spring 코드 → ④ 자주 하는 실수

01

왜 필요한가

서비스마다 로그인을 만들면 생기는 일

문제 — 서비스마다 로그인을 따로 만든다

N배로 늘어나는 것

  • 사용자: 비밀번호 N개
  • 퇴사자 계정 정리: N곳
  • 비밀번호 정책·MFA·보안 패치: N번
  • 감사(누가 언제 로그인했나): N개 로그

서비스나 에이전트가 하나 늘 때마다 같은 일을 반복한다. 에이전트 플랫폼에서는 이 N이 빠르게 커진다.

청중에게 "지금 몇 개 시스템에 따로 로그인하는지" 물어보면 좋다. 핵심은 보안보다 운영 비용이 먼저 체감된다는 점. 그리고 에이전트가 늘어나면 '사용자'뿐 아니라 '프로그램 계정'도 N배가 된다.

용어 — 인증(Authentication)과 인가(Authorization)

인증 · Authentication (AuthN)인가 · Authorization (AuthZ)
질문당신은 누구인가?당신은 이것을 해도 되는가?
순서먼저인증이 끝난 뒤
실패 응답401 Unauthorized — 이름과 달리 "인증 안 됨"403 Forbidden — 누군지는 알지만 권한 없음
비유사원증 발급 (신분 확인)문마다 다른 출입 권한

401이면 로그인으로 보내고, 403이면 안내만 한다. 둘을 섞으면 3회차에서 보게 될 "무한 리다이렉트 루프"가 생긴다.

SSO는 인증 문제를 푼다. 인가는 그 다음 문제이며, 토큰 안의 role/scope로 푼다(2회차). 401의 이름이 Unauthorized라서 헷갈리는데, 실제 의미는 Unauthenticated다.

SSO의 아이디어 — 로그인은 한 곳에서, 앱은 결과만 믿는다

  • IdP (Identity Provider, 신원 제공자): 로그인을 전담하는 서버
  • 앱은 비밀번호를 보지도, 저장하지도 않는다
  • 앱이 받는 것은 IdP가 서명한 토큰뿐
  • 앱 → IdP 관계는 "신뢰": IdP 공개키로 토큰의 진위를 확인

사원증 비유

인사팀(IdP)이 사원증(토큰)을 한 번 발급하면, 모든 문의 리더기(앱)는 사원증만 확인한다. 리더기는 인사 DB를 들여다보지 않는다.

여기서 "앱이 비밀번호를 보지 않는다"를 강조한다. 이게 SSO의 보안상 핵심이다. 에이전트도 IdP가 발급한 토큰을 받는 '앱'의 하나라는 점을 미리 짚어 두면 별도 자료 A2A가 자연스럽다.

"한 번 로그인"이 되는 원리 — IdP 세션 쿠키

앱은 여전히 각자 302로 IdP에 보낸다. 다만 IdP가 자기 쿠키를 보고 로그인 화면을 생략한다. 그래서 '로그아웃'도 앱 세션과 IdP 세션 두 개를 끊어야 한다(뒤에서 다룸).

이 시리즈는 OIDC

OIDC = OAuth 2.0 위에 "로그인(누구인지)"을 얹은 것. 그래서 OAuth 2.0 용어와 흐름을 그대로 쓴다.

Keycloak은 셋 다 지원

SAML은 기존 시스템 연동 때만 만난다. 새로 만드는 앱·API·에이전트는 OIDC로 통일한다.

OAuth 2.0 자체는 인증 프로토콜이 아니라는 점을 짚는다. "Google로 로그인"은 OAuth가 아니라 OIDC다. OAuth만으로 로그인을 흉내 내던 시절의 문제(ID Token 없음, 토큰 대상 불명확)를 OIDC가 정리했다.

OAuth 2.0의 등장인물 4명

  • Resource Owner — 자원의 주인. 보통 사용자
  • Client — 사용자 대신 API를 쓰려는 앱·에이전트
    Spring: spring-boot-starter-oauth2-client
  • Authorization Server — 로그인·동의를 받고 토큰을 발급. IdP = Keycloak
  • Resource Server — 토큰을 검증하고 자원을 주는 업무 API
    Spring: spring-boot-starter-oauth2-resource-server

하나의 Spring 앱이 Client이면서 Resource Server일 수 있다. BFF(3회차)가 그렇다.

Spring 문서가 이 용어를 그대로 쓴다. oauth2Login/oauth2Client는 Client 역할, oauth2ResourceServer는 Resource Server 역할이다. 이 네 단어만 외워도 문서가 읽힌다.

핵심 흐름 — Authorization Code Flow (+ PKCE)

②~⑤는 전부 브라우저가 보는 URL이다. 토큰은 ⑥⑦에서 서버끼리만 주고받는다. 이 분리가 이 흐름의 존재 이유다. ⑤의 경로 /login/oauth2/code/{registrationId}는 Spring Security 기본값이고 Keycloak Client의 Valid redirect URIs에 등록해야 한다.

왜 토큰을 바로 주지 않고 code를 거치나

❌ 토큰을 브라우저 URL로 주면

  • 브라우저 히스토리에 남는다
  • 웹서버·프록시 접근 로그에 남는다
  • 다음 페이지로 갈 때 Referer 헤더로 외부에 새어 나간다
  • 브라우저 확장 프로그램이 읽을 수 있다

옛 "Implicit Flow"가 이렇게 했고, 지금은 사용 금지.

✅ code를 거치면

  • code는 1회용, 수명 약 1분
  • code → 토큰 교환에 client_secret이 필요 → URL에서 code를 훔쳐도 쓸모없다
  • 토큰은 서버 간 백 채널로만 이동
  • state로 요청·응답을 짝지어 CSRF 차단

PKCE (Proof Key for Code Exchange, "픽시")

secret을 가질 수 없는 앱(SPA, 모바일)을 위한 보완. 앱이 난수 code_verifier를 만들고 그 해시 code_challenge를 ②에 보낸 뒤, ⑥에서 원본을 제시한다. code를 가로챈 쪽은 원본을 몰라 교환하지 못한다. 서버 앱도 켜 두는 것이 현재 권고.

"한 단계 더 거치는 게 왜 더 안전하냐"는 질문이 꼭 나온다. 답은 '브라우저에 보이는 것(code)'과 '진짜 열쇠(토큰)'를 분리했기 때문이다. code 자체는 secret 없이는 무용지물이다.

토큰 3종 — 각각 누가 읽고 어디로 가나

토큰누가 읽나담는 것수명 (예)어디에 두나
ID Token앱 (Client)누구인지 — sub, name, email5분 ~ 1시간로그인 처리에만 쓰고 세션에 보관
Access TokenAPI (Resource Server)무엇을 할 수 있나 — aud, scope, roles5 ~ 15분Authorization: Bearer 헤더
Refresh TokenIdP만새 토큰을 받을 권리30분 ~ 30일서버에만. 절대 브라우저·로그에 노출 금지

바꿔 쓰지 말 것

Access Token은 API를 위한 것. 앱이 그 안을 해석해 화면 로직에 쓰면 IdP 설정이 바뀔 때 깨진다. 반대로 ID Token은 API에 보내지 않는다 — API용 aud가 없다.

수명이 짧은 이유

JWT는 발급 후 취소가 어렵다. 탈취돼도 피해가 몇 분으로 끝나도록 Access Token은 짧게, 대신 Refresh Token으로 조용히 갱신한다.

Keycloak 기본값은 access 5분, SSO 세션 idle 30분이다. "짧게"는 보안 설정이 아니라 설계 전제다. 갱신은 Spring의 OAuth2AuthorizedClientManager가 자동으로 해 준다(3회차).

JWT 해부 — header . payload . signature

jwt.io 같은 외부 사이트에 운영 토큰을 붙여 넣지 말 것 — 실습 토큰만. 로컬에서는 payload를 cut -d. -f2 | base64 -d 로 볼 수 있다. 'aud'와 'azp'의 차이(누구용 vs 누가 요청했나)는 2회차에서 다시 다룬다.

API는 토큰을 어떻게 검증하나 — Discovery와 JWKS

공개키는 비밀이 아니다. 누구나 받아갈 수 있고, 그걸로 '검증'만 가능하지 '발급'은 못 한다. 이 비대칭 덕분에 API가 IdP와 비밀을 공유하지 않아도 된다. aud 검사는 Spring 기본값이 아니라는 점을 2회차에서 코드로 본다.

세션 쿠키 vs 토큰 — 둘 다 필요하다

구분세션 쿠키토큰 (JWT)
상태서버가 보관 (stateful)토큰 자체에 포함 (stateless)
검증세션 저장소 조회서명 검증 — 저장소 불필요
취소즉시 (세션 삭제)만료 전엔 어렵다 → 수명을 짧게
전달브라우저가 자동 첨부코드가 Authorization 헤더에 직접 첨부
주요 위험CSRF (자동 첨부의 역효과)XSS로 탈취 (JS가 읽을 수 있으면)
적합브라우저 ↔ 서버서버 ↔ 서버, API, 에이전트

브라우저에는 세션 쿠키, 서버 뒤에서는 토큰. 이 둘을 한 서버에서 합친 것이 3회차의 BFF다. 오늘 만드는 oauth2Login() 앱이 이미 그 형태다 — 브라우저에는 세션 쿠키를 주고, 토큰은 세션 안에 보관한다.

03

Spring으로 붙이기

의존성 2개, 설정 10줄, 로그인 화면 0줄

의존성과 설정 — issuer-uri 하나면 나머지는 자동

build.gradle

dependencies {
  implementation 'org.springframework.boot:spring-boot-starter-web'
  implementation 'org.springframework.boot:spring-boot-starter-security'
  implementation 'org.springframework.boot:spring-boot-starter-oauth2-client'   // "Client" 역할
}

application.yml

spring:
  security:
    oauth2:
      client:
        registration:
          keycloak:                        # registrationId → URL에 쓰임
            client-id: agent-portal
            client-secret: ${KEYCLOAK_CLIENT_SECRET}
            scope: openid, profile, email  # openid 가 있어야 OIDC
        provider:
          keycloak:
            issuer-uri: https://kc.company.com/realms/company

oauth2-client가 맡는 일

로그인 리다이렉트, code → 토큰 교환, 토큰 보관·갱신. 즉 OAuth 2.0의 "Client" 역할 전부. grant type 기본값은 authorization_code.

issuer-uri가 하는 일

{issuer}/.well-known/openid-configuration을 읽어 인증·토큰·JWKS 주소를 자동 설정한다. secret은 환경변수로 — git에 넣지 않는다.

registrationId 'keycloak'은 임의의 이름이지만 로그인 진입점(/oauth2/authorization/keycloak)과 콜백(/login/oauth2/code/keycloak) URL에 그대로 쓰인다. secret은 환경변수로 — git에 넣지 않는다.

SecurityConfig — oauth2Login() 한 줄

SecurityConfig.java

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/css/**", "/actuator/health").permitAll()
                .anyRequest().authenticated())
            .oauth2Login(Customizer.withDefaults());   // ← 이 한 줄
        return http.build();
    }
}

자동으로 생기는 것

  • 로그인 진입점 /oauth2/authorization/keycloak
  • 콜백 /login/oauth2/code/keycloak
  • code → 토큰 교환, PKCE, state 검증
  • 세션 생성 + 세션 쿠키 발급

Keycloak 쪽 설정 1개

Client의 Valid redirect URIs에 http://localhost:8080/login/oauth2/code/keycloak 등록. 안 하면 "Invalid redirect_uri".

로그인 화면 HTML을 한 줄도 쓰지 않는다. 화면은 Keycloak이 제공하고, 디자인은 Keycloak 테마로 바꾼다. 미인증 요청이 오면 Spring이 302로 로그인 진입점에 보낸다 — API 요청에는 이게 문제가 되는데 3회차에서 다룬다.

로그인 후 — 사용자 정보는 어디서 꺼내나

MeController.java

@RestController
public class MeController {

    @GetMapping("/api/me")
    public Map<String, Object> me(@AuthenticationPrincipal OidcUser user) {
        return Map.of(
            "name",   user.getFullName(),
            "email",  user.getEmail(),
            "sub",    user.getSubject(),             // IdP가 준 고유 ID
            "claims", user.getIdToken().getClaims()  // ID Token 전체
        );
    }
}

OidcUser는 ID Token을 풀어 놓은 객체. Service 계층에서는 SecurityContextHolder.getContext().getAuthentication()으로 같은 정보에 접근한다.

Controller에서 request.getHeader("Authorization")을 직접 파싱하지 않는다. 검증은 필터에 맡기고 코드는 결과만 쓴다. 2회차의 Resource Server에서는 OidcUser 대신 Jwt 타입을 받는다.

로그아웃 — 세션이 두 개라는 것을 잊지 말 것

SecurityConfig.java (logout 추가)

@Bean
SecurityFilterChain filterChain(HttpSecurity http,
        ClientRegistrationRepository clients) throws Exception {
    var oidcLogout = new OidcClientInitiatedLogoutSuccessHandler(clients);
    oidcLogout.setPostLogoutRedirectUri("{baseUrl}/");  // 로그아웃 후 돌아올 곳

    http
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .oauth2Login(Customizer.withDefaults())
        .logout(l -> l.logoutSuccessHandler(oidcLogout)); // ← IdP 세션까지 종료
    return http.build();
}

❌ 앱 세션만 끊으면

IdP 세션 쿠키가 남아 다음 접속에서 화면 없이 자동 재로그인. 사용자는 "로그아웃이 안 된다"고 느낀다.

✅ RP-Initiated Logout

앱 세션 삭제 → IdP end_session_endpoint로 302 → IdP 세션 삭제 → 앱으로 복귀. 위 핸들러가 이 흐름을 만든다.

참고: IdP가 먼저 끊은 세션을 앱에 알리는 Back-Channel Logout은 oidcLogout()으로 받는다.

공용 PC 시나리오로 설명하면 잘 와닿는다. 앱 세션만 끊고 자리를 떠나면 다음 사람이 그 앱에 들어갈 때 IdP가 '아직 로그인 중'이라며 통과시킨다.

자주 하는 실수

❌ 서명 검증 없이 payload만 디코딩

Base64는 암호화가 아니다. 누구나 원하는 내용의 "토큰"을 만들 수 있다. 서명 검증이 전부다.

❌ exp · iss 미확인

만료를 안 보면 탈취된 토큰이 영원히 유효. 발급자를 안 보면 다른 IdP의 토큰이 통과.

❌ 토큰을 URL 쿼리에

히스토리·접근 로그·Referer에 남는다. 토큰은 항상 Authorization 헤더로.

❌ aud 미검증

같은 IdP가 발급한 다른 서비스용 토큰이 통과한다. Spring 기본 설정은 aud를 검사하지 않는다 → 2회차 코드.

❌ HTTP 평문 · 로그 출력

Bearer 토큰은 가로채면 그대로 재사용된다. TLS 필수. 로그에 헤더를 통째로 찍지 말 것.

❌ ID Token을 API 인증에 사용

ID Token은 앱이 읽는 것. API에는 aud가 맞는 Access Token만 보낸다.

이 중 'aud 미검증'이 실무에서 가장 흔하다. issuer-uri만 설정하면 같은 realm의 모든 토큰이 통과하기 때문이다. 2회차에서 JwtDecoder에 audience validator를 붙이는 코드를 본다.

요약 · 실습 · 다음 회차

  • 인증은 "누구냐", 인가는 "되냐" — 401 / 403
  • SSO = 로그인은 IdP 한 곳, 앱은 토큰만 검증
  • "한 번 로그인"은 IdP 세션 쿠키가 만든다
  • code flow: 토큰은 백 채널로만, PKCE는 기본으로
  • ID Token은 앱이, Access Token은 API가 읽는다
  • JWT는 서명된 JSON — 공개키로 검증, 수명은 짧게
  • Spring: 의존성 2개 + issuer-uri + oauth2Login()
