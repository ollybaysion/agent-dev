OAuth 2.0 — 권한을 빌려주는 규칙

인가 프레임워크: 왜 생겼나 · 승인 방식 · 토큰의 범위와 보호 장치

대상: 1회차(SSO)를 본 에이전트 개발자 · 로그인(누구인지)은 보충 B · 약 35분

이 자료의 위치 — 1회차 '개념' 장을 한 단계 깊게

  • 1회차는 OAuth 2.0을 로그인에 필요한 만큼만 다뤘다
  • 이 자료는 OAuth 2.0 자체를 다룬다 — 왜 생겼고, 승인 방식이 몇 가지이며, 토큰을 어떻게 좁히고 지키는가
  • "누가 로그인했나"는 OAuth 2.0이 답하지 않는다 → 보충 B · OIDC
  • 끝나면 Spring 설정의 registration · provider · authorization-grant-type이 규격의 어느 조각인지 읽힌다

한 문장 정의

OAuth 2.0은 비밀번호를 넘기지 않고, 사용자가 앱에게 범위가 정해진 열쇠(토큰)를 빌려주는 절차를 정한 규격이다 (RFC 6749, 2012).

01

왜 생겼나

비밀번호를 넘겨주던 시절의 문제

시간 배분: 이 장 5분 (누적 7분).

문제 — 제3자 앱에 비밀번호를 그대로 주던 시절

2010년 이전, "가계부 앱이 내 은행 거래 내역을 가져오려면?"

  • 앱에 은행 아이디와 비밀번호를 입력한다
  • 앱이 나인 척 은행에 로그인해 긁어 온다

무엇이 문제인가

  • 전부 아니면 전무 — 조회만 허락할 방법이 없다. 이체도 된다
  • 취소 불가 — 앱을 끊으려면 비밀번호를 바꿔야 하고, 그러면 다른 앱도 전부 끊긴다
  • 비밀번호가 여러 곳에 저장 — 앱 하나가 뚫리면 은행 계정이 뚫린다
  • MFA·SSO 불가 — 앱이 비밀번호를 대신 치는 구조에서는 2단계 인증을 넣을 수 없다
실제로 2000년대 중반 트위터·구글 API 연동 앱들이 이렇게 했고, 그 반성에서 OAuth 1.0(2007)과 2.0(2012)이 나왔다. 에이전트 시대에 이 문제가 다시 나타난다: 에이전트에게 사용자 비밀번호를 주고 싶어지는 유혹. 별도 자료 A2A에서 다룬다.

해결 — 비밀번호 대신 "범위와 기한이 있는 열쇠"를 빌려준다

  1. 앱은 비밀번호를 보지 않는다. 사용자를 Authorization Server로 보낸다
  2. 사용자는 거기서 직접 로그인하고, 앱이 요청한 범위(scope)에 동의한다
  3. 앱은 그 범위만 되는 Access Token을 받는다
  4. API는 토큰을 검증하고, 범위 안의 요청만 들어준다
역할 (RFC 6749)이 예에서이 시리즈에서
Resource Owner사용자 kim사용자
Client가계부 앱Spring 앱 · 에이전트
Authorization Server은행 인증 서버Keycloak
Resource Server은행 API업무 API
1회차 11번 슬라이드의 등장인물 4명과 같은 그림이다. 차이는 앞 슬라이드와 나란히 놓고 "빨간 화살표가 사라졌다"를 보여주는 것. OAuth 2.0은 결국 이 한 가지를 위해 존재한다.
02

승인 방식 (Grant)

토큰을 받는 길은 여러 갈래 — 사람이 있느냐 없느냐로 갈린다

시간 배분: 이 장 13분 (누적 20분). grant 지도 2분, code 흐름 HTTP 4분, client credentials 3분, refresh 2분, 폐기된 방식 2분.

Grant 지도 — 6가지 중 쓰는 건 둘, 버린 건 둘

승인 방식사용자누가 쓰나어떻게상태
Authorization Code (+PKCE)있음 (브라우저)웹앱 · SPA · 모바일 · BFF302로 로그인 → code → 백 채널에서 토큰 교환표준
Client Credentials없음배치 · 서비스 간 · 에이전트client_id + secret으로 바로 토큰표준
Refresh Token(로그인 때 받음)위 둘을 쓰는 모든 Clientrefresh → 새 access (사용자 개입 없음)표준
Device Code있음 (다른 기기)TV · CLI · 입력 장치 없는 기기화면에 코드 표시 → 폰에서 승인표준
Implicit있음(옛) SPA토큰을 URL fragment로 직접 전달폐기
Password (ROPC)있음(옛) 자사 앱앱이 비밀번호를 받아 토큰과 교환폐기

이 시리즈에서 쓰는 둘

사람이 있으면 Authorization Code, 없으면 Client Credentials. 2회차에서 Keycloak으로 둘 다 발급해 보고, 별도 자료 A2A에서 에이전트가 둘 사이를 오가는 문제(위임)를 다룬다.

고르는 기준은 하나

"이 토큰은 누구의 권한인가?" 사용자의 권한이면 사용자가 직접 로그인해야 하고(code), 앱 자체의 권한이면 앱이 자기 자격으로 받는다(client credentials).

Device Code는 에이전트 CLI 도구에서 의외로 자주 만난다(gh auth login이 이 방식). 표에는 넣되 시간은 쓰지 않는다. Implicit과 ROPC는 11번 슬라이드에서 왜 버렸는지만 설명한다.

Authorization Code — 실제 HTTP 4개

① 브라우저 → AS (302의 목적지)

GET /realms/company/protocol/openid-connect/auth
    ?response_type=code
    &client_id=agent-portal
    &redirect_uri=https://app/login/oauth2/code/keycloak
    &scope=accounts:read          # OIDC면 openid 추가
    &state=af0ifjsldkj            # 요청·응답 짝 맞추기
    &code_challenge=E9Melhoa…     # PKCE
    &code_challenge_method=S256

② AS → 브라우저 (로그인·동의 후)

HTTP/1.1 302 Found
Location: https://app/login/oauth2/code/keycloak
          ?code=SplxlOBeZQQYbYS6WxSbIA&state=af0ifjsldkj

③ 앱 서버 → AS (백 채널)

POST /realms/company/protocol/openid-connect/token
Content-Type: application/x-www-form-urlencoded
Authorization: Basic base64(client_id:client_secret)

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https://app/login/oauth2/code/keycloak
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r…

④ 응답 (JSON)

{ "access_token": "eyJhbGciOiJSUzI1NiIs…",
  "token_type": "Bearer", "expires_in": 300,
  "refresh_token": "eyJhbGciOiJIUzI1NiIs…",
  "scope": "accounts:read" }

①②는 브라우저 주소창에 보인다. ③④는 서버끼리만. ③에서 redirect_uri를 다시 보내는 이유: ①과 같은지 비교해 code 바꿔치기를 막기 위해.

1회차 12번 시퀀스 그림의 ②④⑥⑦을 실제 바이트로 보여주는 슬라이드. 주소창에 보이는 것(code, state)과 안 보이는 것(secret, verifier, 토큰)을 색으로 구분하지 않아도 좌우 칼럼으로 나뉜다. Keycloak 경로에 openid-connect가 들어가지만 scope에 openid가 없으면 순수 OAuth 2.0으로 동작한다.

Client Credentials — 사람이 없을 때, 앱 자신의 권한으로

HTTP 1개로 끝난다

POST /realms/company/protocol/openid-connect/token
Content-Type: application/x-www-form-urlencoded
Authorization: Basic base64(client_id:client_secret)

grant_type=client_credentials
&scope=report:write

HTTP/1.1 200 OK
{ "access_token": "eyJhbGciOi…", "token_type": "Bearer",
  "expires_in": 300 }                # refresh_token 없음

Spring — registration 하나 더

spring.security.oauth2.client.registration:
  report-agent:
    client-id: report-agent
    client-secret: ${REPORT_AGENT_SECRET}
    authorization-grant-type: client_credentials
    scope: report:write
    provider: keycloak            # 같은 provider 재사용

무엇이 다른가

  • 리다이렉트도, 로그인 화면도, 동의도 없다
  • 토큰의 주체(sub)는 사용자가 아니라 앱 자신 — Keycloak에서는 Service Account
  • refresh token이 없다. 만료되면 그냥 다시 받는다 (secret이 곧 갱신 자격)

에이전트의 기본 자세, 그러나

배치·야간 작업·시스템 간 호출에는 이게 맞다. 그런데 "kim 대신" 하는 일을 이 토큰으로 하면 API는 kim을 모른다 — 감사 로그에 에이전트만 남는다. 그 간극이 별도 자료 A2A(위임, Token Exchange)의 주제다.

Spring에서 쓰기

OAuth2AuthorizedClientManager가 만료를 보고 알아서 재발급. 2회차 코드 참조.

"에이전트는 전부 client credentials면 되는 거 아니냐"는 질문이 나오면 warn 카드로 답한다. 맞는 경우와 틀린 경우의 경계가 '누구의 권한인가'다. 2회차에서 Keycloak Service Account를 실제로 만든다.

Refresh Token — 짧은 Access Token을 조용히 이어 붙인다

갱신 요청 (백 채널)

POST /…/token
Authorization: Basic base64(client_id:secret)

grant_type=refresh_token
&refresh_token=eyJhbGciOiJIUzI1…

→ 새 access_token + 새 refresh_token

Rotation

갱신할 때마다 refresh token도 새로 발급하고 옛것은 폐기. 옛것이 다시 쓰이면 탈취로 보고 계열 전체를 취소한다. Keycloak: Revoke Refresh Token 옵션.

보관 규칙: 서버 세션에만. 브라우저·로그·URL에 나오면 안 된다. 이게 3회차 BFF가 필요한 이유의 절반이다.

"access 5분이면 사용자가 5분마다 로그인하냐"는 오해를 그림으로 푼다. 짧은 access + 긴 refresh의 조합이 '탈취 피해 창은 짧게, 사용자 경험은 길게'를 동시에 만족시킨다. 3회차에서 Spring이 이 갱신을 어떻게 자동으로 하는지 본다.

왜 Implicit과 Password를 버렸나 — 그리고 OAuth 2.1

❌ Implicit — 토큰을 브라우저 URL로

#access_token=eyJ… 처럼 fragment에 실어 보냈다. 서버 없는 SPA를 위한 지름길.

  • 토큰이 히스토리 · Referer · 확장 프로그램에 노출
  • 발급 과정에 Client 인증이 없다 — 누가 받아 가는지 확인 불가
  • refresh token을 줄 수 없어 UX도 나빴다

대체: Code + PKCE. SPA는 BFF(3회차)로.

❌ Password (ROPC) — 앱이 비밀번호를 받는다

앱 화면에 아이디·비밀번호를 입력받아 토큰과 교환. "자사 앱이니까 괜찮다"는 논리.

  • 4번 슬라이드의 문제가 전부 되살아난다 — OAuth의 존재 이유를 부정
  • MFA · 소셜 로그인 · 비밀번호 없는 로그인이 전부 불가
  • 앱 코드에 비밀번호가 지나간다 — 로그에 남기 쉽다

대체: 사람은 Code, 에이전트는 Client Credentials.

OAuth 2.1 (draft) = 2.0 + 10년치 보안 권고(BCP)를 본문에 합친 것

PKCE를 모든 Client에 필수 · Implicit과 ROPC 삭제 · redirect_uri는 문자열 완전 일치 · Bearer 토큰을 쿼리 스트링에 금지 · refresh token은 rotation 또는 sender-constrained. 새 기능이 아니라 "이미 그렇게 해야 했던 것"의 정리다. MCP 인증(A2A 자료)이 2.1을 요구한다.

ROPC는 Keycloak에서 "Direct Access Grants" 체크박스다. 기본값이 켜져 있는 버전이 있으니 2회차에서 끄는 것을 보여준다. 테스트 자동화에서 ROPC를 쓰고 싶어하는데, 그것도 client credentials나 테스트용 토큰 발급으로 바꾼다.
03

토큰과 보호 장치

Bearer의 의미 · 범위를 좁히는 두 축 · 흐름을 지키는 네 가지

시간 배분: 이 장 12분 (누적 32분). Bearer/형식 3분, scope·aud 4분, 보호 장치 3분, Client 종류 2분.

Access Token — "Bearer"는 가진 사람이 임자라는 뜻

Bearer = 소지자

지하철 승차권과 같다. 누가 내는지 묻지 않는다. 그래서 훔치면 그대로 쓸 수 있다. 방어는 셋뿐: TLS · 짧은 수명 · 로그와 URL에 남기지 않기.

규격은 토큰의 생김새를 정하지 않는다

RFC 6749에는 JWT라는 단어가 없다. Authorization Server가 알아보기만 하면 된다. JWT 형식의 access token은 별도 규격(RFC 9068).

Keycloak은 JWT. 그래서 API가 Keycloak에 묻지 않고 공개키로 검증한다(1회차 16번). 대신 취소가 즉시 반영되지 않으니 수명을 짧게 둔다.

Opaque (불투명) 토큰JWT (자기 서술) 토큰
생김새난수 문자열 2YotnFZFEjr1zCsicMWpeyJhbGciOi… — 서명된 JSON
API가 검증하는 법AS의 Introspection 엔드포인트에 매번 묻는다 (RFC 7662)AS 공개키(JWKS)로 로컬 서명 검증
요청당 네트워크1회 (AS 호출)0회 (키는 캐시)
취소즉시 반영만료(exp)까지 유효
내용 노출없음 — AS만 안다payload는 Base64, 누구나 읽는다
적합민감하고 취소가 중요한 곳마이크로서비스 · 고트래픽 API

둘을 섞기도 한다: 브라우저 밖으로 나가는 토큰은 opaque, 내부 서비스 간에는 JWT ("phantom token" 패턴).

JWT의 payload를 읽을 수 있다는 점 때문에 "토큰에 개인정보를 넣지 말라"는 원칙이 나온다. Keycloak 기본 access token에 email·name이 들어가는데, 2회차에서 Mapper로 뺄 수 있음을 보여준다.

범위를 좁히는 두 축 — scope는 "무엇을", aud는 "어디에"

  • scope — 할 수 있는 동작. Client가 요청, 사용자가 동의, AS가 줄일 수 있다. 결과는 응답의 scope
  • aud — 받아 줄 API. 없으면 같은 AS의 토큰이 어느 API에나 통과
  • aud 지정: 요청에 resource=… (RFC 8707). Keycloak은 Audience Mapper
  • API의 판정: aud 불일치 401, scope 부족 403

Spring: scope → SCOPE_xxx 권한 자동. aud는 기본 검사 안 함 → JwtDecoder validator (2회차).

1회차 '자주 하는 실수'의 aud 미검증을 원리 쪽에서 다시 본다. 에이전트가 여러 API를 부를 때 토큰 하나로 다 부르고 싶어지는데, A2A 자료의 '최소 aud' 원칙이 여기서 나온다.

흐름을 지키는 네 가지 — 하나라도 빠지면 code가 열쇠가 된다

✅ state — 요청과 응답을 짝짓는다

앱이 난수를 만들어 ①에 보내고 세션에 둔다. 콜백 ②의 state가 다르면 버린다.
막는 것: 공격자가 자기 code를 내 브라우저에 심어, 내 세션을 공격자 계정에 묶는 로그인 CSRF.

✅ PKCE — code를 훔쳐도 못 바꾼다

난수 code_verifier의 해시를 ①에, 원본을 ③에. 해시만 본 쪽은 원본을 모른다.
막는 것: 리다이렉트 URL에서 code 가로채기 (모바일 커스텀 스킴, 악성 확장). 2.1에서 모든 Client 필수.

✅ redirect_uri 완전 일치

AS는 등록된 URI와 문자열이 똑같을 때만 code를 보낸다. 와일드카드·접두사 일치 금지.
막는 것: https://app/*로 등록해 두면 앱 안의 open redirect 하나로 code가 외부로 흘러간다.

✅ 1회용 · 짧은 code, 짧은 토큰

code는 1회 사용 후 폐기, 수명 약 1분. 같은 code가 두 번 오면 그 code로 발급한 토큰까지 취소.
막는 것: 로그·히스토리에서 code를 주워 뒤늦게 교환하기.

Keycloak 주의: Valid Redirect URIs에 *나 http://localhost:*를 운영 realm에 남겨 두는 실수가 가장 흔하다. Spring은 state와 PKCE를 자동으로 만들지만, secret이 있는 Client에는 PKCE를 자동으로 켜지 않는다 — OAuth2AuthorizationRequestCustomizers.withPkce()로 명시.

각 장치가 '어떤 공격을' 막는지를 한 줄씩 붙였다. 네 가지는 서로 다른 구멍을 막기 때문에 하나가 다른 하나를 대신하지 못한다. Spring의 PKCE 자동 적용 조건은 공식 문서 기준: client-authentication-method가 none이거나 secret이 없을 때.

이 시리즈의 선택

FE가 SPA여도 토큰은 BFF(Confidential)가 들게 한다(3회차). 에이전트는 서버에서 돌리는 한 Confidential — secret을 환경 변수·Vault에 두고 주기적으로 회전한다.

secret을 Public Client에 심으면

JS 번들·APK에서 10초면 꺼낸다. 그 순간 누구나 그 Client 행세를 할 수 있다. "숨겨 두면 괜찮다"는 가정이 성립하지 않는 쪽이 Public이다.

Keycloak 콘솔에서 Client 만들 때 가장 먼저 묻는 토글이 Client authentication이다. 이 슬라이드가 그 토글의 의미다. 2회차에서 실제로 켜고 끈다.

spring.security.oauth2.client — registration 둘

registration:
  keycloak:                 # 사람: code flow
    client-id: agent-portal
    client-secret: ${PORTAL_SECRET}
    scope: openid, profile, email
  report-agent:             # 에이전트
    client-id: report-agent
    client-secret: ${AGENT_SECRET}
    authorization-grant-type: client_credentials
    scope: report:write
    provider: keycloak
provider:
  keycloak:                 # 1회차와 같은 값
    issuer-uri: ${KC_ISSUER}
    # = https://kc.company.com/realms/company

같은 Keycloak, 같은 provider, 서로 다른 Client 둘. 1회차 설정에 아래 블록 하나가 더 붙은 것이다.

issuer-uri 한 줄로 끝나는 것은 OAuth 2.0이 아니라 OIDC Discovery 덕분이다. 순수 OAuth 2.0 서버(예: GitHub)는 authorization-uri, token-uri를 손으로 적어야 한다. 이 차이가 보충 B로 넘어가는 연결 고리다.

자주 하는 실수

❌ "간단하니까" ROPC

앱 로그인 폼에서 비밀번호를 받아 토큰 교환. 4번 슬라이드의 문제가 전부 되살아나고, MFA를 영영 못 넣는다.

❌ redirect_uri 와일드카드

https://app/* 등록. 앱 안의 open redirect 하나로 code가 공격자에게 간다. 운영 realm에서 localhost도 지울 것.

❌ access token으로 "누구인지" 판단

access token은 API용 열쇠다. 앱이 그 안의 email을 읽어 로그인 처리하면 토큰 바꿔치기에 뚫린다 → 보충 B.

❌ scope를 항상 최대로

"나중에 쓸지 모르니" 전부 요청. 탈취 피해 범위가 그만큼 커진다. 동작마다 필요한 scope만, 에이전트는 더 좁게.

❌ secret을 SPA · 모바일에

번들에서 바로 꺼낸다. Public Client에는 secret 없이 PKCE, 또는 BFF로 Confidential화.

❌ 토큰을 쿼리 스트링 · 로그에

Bearer는 가진 자가 임자. 접근 로그 한 줄이 곧 탈취다. 헤더로만, 로그에는 마스킹.

1회차 실수 슬라이드와 겹치지 않게 '흐름' 쪽 실수만 모았다. 세 번째 카드가 보충 B의 도입부다.

요약 · 다음 자료

  • OAuth 2.0 = 비밀번호 대신 범위·대상·기한이 있는 토큰을 빌려주는 절차
  • 승인 방식은 "누구의 권한인가"로 고른다 — 사람은 Code+PKCE, 앱 자신은 Client Credentials
  • Implicit · Password는 폐기. OAuth 2.1은 그 정리본
  • Access Token은 Bearer — 짧게, TLS로, 로그 밖으로. refresh로 이어 붙인다
  • scope는 무엇을, aud는 어디에. 둘 다 좁게. aud 검사는 Spring에서 직접 켠다
  • state · PKCE · redirect_uri 완전 일치 · 1회용 code — 서로 다른 구멍을 막는다
  • secret을 지킬 수 있으면 Confidential, 아니면 Public(PKCE 필수) 또는 BFF

보충 B — OIDC

OAuth 2.0은 "이 앱이 뭘 해도 되나"까지만 답한다. "지금 로그인한 사람이 누구인가"를 표준으로 답하려고 그 위에 얹은 것이 OIDC다. ID Token · 표준 claim · Discovery · 로그아웃.
